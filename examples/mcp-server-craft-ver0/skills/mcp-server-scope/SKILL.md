# MCP Server Scope

## 상태

`ver0` draft. 실제 제작 요청에서 도구 수와 transport 선택 기준을 수정할 예정입니다.

## 목적

MCP 서버의 **목적, 작업 표면, 전송 방식**을 구현 전에 고정합니다. 백엔드 API 목록이 아니라 Agent가 끝낼 작업을 단위로 잡습니다.

## 사용 시점

- 새 MCP 서버를 만들기 전
- 기존 서버에 도구를 추가하기 전, 범위가 불명확할 때
- `mcp-server-craft` 전체 흐름의 첫 단계

## 입력

- Agent가 반복해서 하는 작업 (예: 사내 문서 검색)
- 백엔드 시스템
- 사용자 범위 (개인 / 팀)
- 개인 클라우드 키로 백엔드를 칠 수 있는지
- 읽기 vs 쓰기
- 클라이언트 (Cursor, Claude Code 등)

## 절차

### 1. 작업 한 문장

다음을 한 문장씩 적습니다.

- Agent가 이 서버로 **무엇을 끝내는가**
- 누가 쓰는가 (개인 로컬 / 팀 공유)
- 개인 자격 증명으로 백엔드를 부르면 되는가, 공유 서버가 필요한가
- 완료와 실패를 어떻게 구분하는가

문장이 API 제품명(“검색 API를 연다”)이면 작업으로 다시 씁니다 (“회의 전에 관련 사내 문서를 찾는다”).

### 2. 기존 서버

같은 작업을 여는 공식·사내 MCP가 있으면 이름을 적고, 이 Skill을 여기서 끝냅니다. 연결은 `mcp-server-connect`로 넘깁니다.

### 3. 프리미티브 선택

| 종류 | 쓸 때 | 쓰지 않을 때 |
|---|---|---|
| 도구 | 검색, 조회, 생성 등 Agent가 인자를 넣어 호출 | 고정 문서를 매번 읽기만 할 때 |
| 리소스 | URI로 읽는 컨텍스트 (스키마, 최신 정책 문서) | 검색·필터·쓰기가 필요할 때 |
| 프롬프트 | 팀이 반복하는 질의 템플릿 | 도구 설명으로 충분한 때 |

도구 수는 **그 작업에 필요한 만큼만**. 참고 서버는 사내 검색을 `retrieve` **하나**로 연다. 3~8개를 목표로 채우지 않습니다. 그보다 많으면 서버를 나누거나, 한 도구의 입력을 넓혀 메서드 나열을 줄입니다.

쓰기 도구는 요청에 있을 때만 포함합니다. 컨텍스트 서버 기본은 읽기입니다.

### 4. 도구 스케치

각 도구에 이름, 한 줄 설명, 입력, 성공 시 반환 요약을 적습니다. 백엔드 메서드명을 도구명으로 쓰지 않습니다.

참고 스케치 (`purple-context-mcp`, 복제 대상 아님):

| 도구 | Agent 작업 | 워크로드 권한 힌트 |
|---|---|---|
| `retrieve` | 사내 문서·코드 의미 검색 | 검색 백엔드 읽기 하나 |

Drive 목록, 메일, 관리자 API는 목적에 없으면 제외합니다.

### 5. 전송 선택

| 조건 | 선택 |
|---|---|
| 개인 로컬, Cursor가 프로세스를 띄움 | stdio |
| 팀이 같은 서버를 쓰거나 클러스터에서 연다 | Streamable HTTP. 요청마다 transport를 새로 만들면 **stateless**(세션·SSE GET 없음) |
| 구형 SSE만 있는 기존 서버 | 유지하되, 신규는 SSE를 기본으로 두지 않음 |

선택 이유를 한 줄로 적습니다.

### 6. 하지 않을 것

포함하지 않는 도구, 열지 않는 권한, 이번에 만들지 않는 배포를 명시합니다.

## 출력 형식

```md
## 범위 요약

- 목적:
- 사용자: 개인 / 팀
- 전송: stdio / Streamable HTTP — 이유 (stateless 여부)
- 공유 서버: 필요 이유 / 로컬만
- 기존 서버 재사용: 없음 / 이름

## 표면

| 이름 | 종류 | 설명 | 입력 | 권한 힌트 |
|---|---|---|---|---|

## 하지 않을 것

## 가정
```

## 완료 조건

- 목적이 Agent 작업 문장으로 적힘
- 공유 서버가 필요한지와 이유가 있음
- 기존 서버 재사용 여부를 판단함
- 도구가 API 메서드 나열이 아님
- 읽기 기본, 쓰기는 명시된 것만
- transport와 제외 범위가 있음

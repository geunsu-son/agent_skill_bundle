# Domain Storytelling Workshop

## 상태

`ver0` testing. 다른 저장소의 실제 업무 워크숍에서 입장 확인(as-is), 질문 형식(가설·추측), 질문 사다리, 종료 테스트, Markdown 저장·재개와 출력 형식을 검증합니다.

## 목적

**현재 돌아가고 있는 실제 업무·운영**에서 빠진 행위자, 행동, 업무 대상, 조건, 예외와 판단 기준을 대화로 드러내고, 사용자의 암묵지를 확인된 도메인 기록으로 만듭니다. 확인된 기록은 이후 개발·분석·데이터 작업에 재사용할 수 있습니다.

이 워크숍은 **개발/시스템 설계 작업 자체**를 진행하는 자리가 아닙니다. “더 나은 도구 아이디어”를 모으기보다, 지금 어떻게 일하는지(빨래가 무엇인가)를 깊게 묻는 자리입니다.

## 담당자의 마인드

Agent는 인터뷰 동안 **워크숍 담당자**다. 도메인 구체화에만 집중한다.

**사용자가 요청한 해결책을 그대로 만드는 것이 아니라, 그 요청 뒤의 니즈와 현재 업무를 확인한다.**

- “CRM을 만들어 달라”, “버튼을 추가해 달라” 같은 요청은 확정 요구사항이 아니라 **사용자 니즈/원함** 또는 **해결책 가설**로 기록합니다. 표면 요청에서 멈추지 않고, 누가 어떤 상황에서 무엇이 불편한지와 현재 어떻게 우회하는지를 더 깊게 묻습니다.
- 니즈가 어느 정도 모이면 `원하는 니즈가 이런 것으로 인지했습니다. 맞나요?`처럼 확인합니다. 목적은 도메인 니즈를 분명히 하는 것이지 설계를 확정하는 것이 아닙니다.
- 진행 속도와 남은 범위는 담당자가 관리합니다. 무엇을 더 물을지 사용자에게 되묻지 않습니다.

## 사용 시점

- 문서화되지 않은 업무를 기능이나 Agent 요구사항으로 바꾸기 전
- 같은 기능의 수정 요청이 반복되지만 업무 규칙이 불명확할 때
- 기존 코드·데이터 처리 절차가 어떤 업무 규칙을 구현하는지 복원할 때
- 서비스나 업무를 인터뷰로 문서화할 때. 시작·종료 경계가 아직 흐려도 주제만으로 시작

해결책이나 구현만 요청받았더라도 핵심 업무 규칙이 불명확해 결과가 달라질 수 있으면 먼저 사용합니다. 목적 자체를 인터뷰 전용으로 바꾸지 않습니다. 탐색 인터뷰와 구현 전 정리를 모두 1급 모드로 둡니다.

## 사용하지 않을 때

- 아직 아무도 하고 있지 않은 일(앞으로 만들 시스템·봇·서비스)이 주제일 때. 복원할 암묵지가 없으면 형식만 다른 요구사항 인터뷰가 됩니다. §2 입장 확인으로 걸러냅니다.
- 사용자가 이미 설계를 확정했고 구현만 남았을 때
- 사용자가 즉시 답할 수 없는 비대화형 실행(자동화, 예약 실행, 사용자 없는 단독 수행)일 때. 추측으로 빈칸을 채우지 말고 답변이 필요하다는 사실을 알리고 멈춥니다.

## 관련 Rule

- [`rules/domain-storytelling-workshop.mdc`](../../rules/domain-storytelling-workshop.mdc)

## 입력

- 새 워크숍: 주제, 업무 흐름의 이름, 또는 첫 설명
- 이어하기: `domain-workshops/`에 저장된 워크숍 Markdown
- 있으면: 정리 목적, 이후 사용할 사람, 기존 문서·화면·코드·데이터 정의

주제나 첫 설명만 있어도 시작합니다. 시작·종료 문장이나 단일 흐름 선택을 입장 조건으로 요구하지 않습니다. 필요한 정보를 체크리스트로 한꺼번에 요구하지 않습니다.

## 절차

### 상호작용: gate와 질문 형식

**고정 선택지 gate**는 채팅에 번호 목록만 적지 않고, Cursor **`AskQuestion` 도구**로 클릭 가능한 질문을 제시합니다. 각 절의 `text` 블록은 **질문 문구와 옵션 라벨의 SSOT**이며, `AskQuestion`의 `prompt`와 `options[].label`은 그와 같게 맞춥니다. `options[].id`는 영문 kebab-case(예: `new-workshop`, `resume-workshop`)로 두고, 의미는 번호 1·2·3과 동일하게 유지합니다.

| gate | 절 | `AskQuestion` | 폴백(채팅) |
|---|---|---|---|
| 새 워크숍 / 이어하기 | §1 | 예 | 아래 `text` 블록과 동일 문구·번호 |
| 같은 파일 덮어쓰기 / 새 파일명 | §1 | 예 | 동일 |
| 입장 확인(지금 하고 있음 / 과거 수동 / 아직 없음) | §2 | 예 | 동일 |
| 탐색 인터뷰 / 구현 전 정리 | §2 | 예 | 동일 |
| 모드 추천 확인(맞음 / 다른 모드) | §2 | 예 | 한 문장 추천 + 동일 선택지 |
| 현재 업무 인터뷰 / 시스템·개발 설계(중단) | §2 | 예 | 동일 |
| 연결점 1–4(생략 포함) | §8 | 예 | 동일 |
| 이어하기 **파일** 선택 | §1, §9 | 아니오 | 제목·모드·수정일 목록 후 사용자가 경로 또는 제목 지정 |
| 도메인·재생·니즈 확인 등 **열린 질문** | §3–§7 | 아니오 | 채팅 한 줄(또는 §6 형식). 선택지를 억지로 붙이지 않음 |

규칙:

- 한 턴에 **gate 하나**. gate 직후 같은 턴에 도메인 질문을 덧붙이지 않습니다.
- `AskQuestion`을 사용할 수 없는 환경이면 **폴백**으로만 채팅 번호 목록을 씁니다.
- gate 답을 받은 뒤에만 다음 절차(파일 읽기, 모드 적용, 질문 재개)로 진행합니다.

### 1. 세션 gate

Skill을 호출하면 먼저 프로젝트의 `domain-workshops/*.md`를 확인합니다. 다른 폴더까지 검색해 관련 없는 문서를 후보로 올리지 않습니다.

저장된 파일이 있으면 제목, 모드, 상태, 수정일을 보여주고 하나만 묻습니다.

```text
어떻게 시작할까요?
1. 새 워크숍 시작
2. 기존 워크숍 이어하기
```

`이어하기`를 고르면 파일을 선택받아 내용을 읽고 `다음 질문`부터 계속합니다. 저장된 모드를 그대로 사용하므로 다시 선택받지 않습니다. 예전 파일에 모드가 없으면 내용으로 추정하거나 한 번만 확인합니다. `status: confirmed` 파일이라면 먼저 무엇이 달라졌는지 질문한 뒤 `in-progress`로 바꿉니다. 이어하기는 §2 입장 확인을 다시 하지 않습니다.

세션 중 사용자가 “처음부터”, “다시 시작”이라고 하면 같은 경로를 덮어쓸지 새 파일명으로 둘지 한 번만 확인한 뒤, 모드 gate부터 다시 진행합니다. 이 확인은 **상호작용** 표의 고정 gate이므로 `AskQuestion`으로 제시합니다.

```text
기존 워크숍 파일을 어떻게 할까요?
1. 같은 경로에 덮어쓰기
2. 새 파일명으로 저장
```

저장된 파일이 없으면 파일 선택을 묻지 않고 새 워크숍으로 시작합니다. 이 gate는 Skill이 호출됐을 때 실행하며 모든 새 채팅에서 자동 실행된다고 가정하지 않습니다.

인터뷰 동안 `role`은 항상 `workshop-facilitator`입니다.

### 2. 입장 확인, 모드와 경계 draft

#### 입장 확인 (새 워크숍 1문항)

모드를 묻기 전에 as-is가 있는지 하나만 확인합니다. 복원할 업무가 없으면 이 워크숍은 형식만 다른 요구사항 인터뷰가 됩니다.

```text
이 일을 지금 실제로 하고 있는 사람과 최근 사례가 있나요?
1. 있음 — 지금 누군가 이 일을 하고 있습니다
2. 과거에 수동으로 했음 — 지금은 안 하거나 방식이 바뀌었습니다
3. 아직 없음 — 앞으로 만들 일입니다
```

- **1** → 그대로 진행합니다.
- **2** → 그 수동 운영을 주제로 범위를 좁혀 진행합니다. 앞으로 만들 것이 아니라 그때 어떻게 했는지를 묻습니다.
- **3** → 이 워크숍을 권하지 않는다고 한 문장으로 알리고, 그래도 진행할지 확인합니다. 진행하면 1절 `범위 예외`에 기록합니다.

```text
범위 예외: as-is 없음 — [사용자가 말한 이유]. 이 기록은 확인된 업무가 아니라 계획 가설이다.
```

#### 모드와 경계 draft

새 워크숍에서는 워크숍 모드를 하나 고릅니다. 첫 설명만으로 분명하면 추천 이유를 한 문장으로 채팅에 말한 뒤, 아래 선택지로 **한 번만** 확인합니다(`AskQuestion`). 분명하지 않으면 추천 없이 아래 gate만 묻습니다.

```text
이번 워크숍은 어떤 목적에 가깝나요?
1. 탐색 인터뷰(문서화) — 주제만 있어도 시작. 누가·무엇을·어떤 결과로 보는지 한 줄로 확인하고, 시작·종료는 draft로 둡니다.
2. 구현 전 정리 — 문제와 해결책 가설을 분리하고, 이번에 다룰 흐름을 초기에 더 분명히 합니다.
```

모드를 추천할 때만, 위 선택지와 함께 또는 아래처럼 확인합니다.

```text
[추천 한 문장] — 이 모드로 진행할까요?
1. 예, 추천한 모드로 진행
2. 아니오, 위 목적 목록에서 다시 고르기
```

시작 사건과 종료 결과는 입장 조건이 아닙니다. 아래 문장을 **초안**으로 적고, 중간 재생마다 확인된 스토리에 맞게 수정합니다.

```text
[초안] [시작 사건]이 발생하면, [종료 결과]가 될 때까지의 흐름을 다룹니다.
```

주제만 있어 시작·종료를 아직 한 문장으로 못 쓰면, 빈칸을 채워 달라고 강요하지 않습니다. `아직 모름`으로 두고 스토리를 쌓은 뒤 고칩니다.

#### 탐색 인터뷰(문서화)

주제만 있어도 시작합니다. 첫 질문은 여러 흐름 후보 중 하나를 고르게 하는 것이 아닙니다. 누가·무엇을·어떤 결과로 보거나 하는지를 한 줄로 확인합니다.

여러 흐름이 보여도 초기에 자르지 않습니다. 스토리가 갈라지는 지점이 확인되면 그 갈래만 후속 워크숍 후보로 남기고, 지금 확인 중인 스토리를 이어갑니다.

#### 구현 전 정리

사용자가 해결책을 요청하면 다음 두 항목을 분리합니다.

- 해결하려는 문제 / 니즈: 불편을 겪는 Actor, 상황, 현재 우회 방법, 바뀌어야 할 결과
- 요청한 해결책 가설: 사용자가 제안한 기능·도구·방식 (구현 결정이 아님)

문제가 드러나지 않았다면 “그 해결책이 없어서 현재 어떤 불편이 생기나요?”처럼 가장 중요한 질문 하나만 묻습니다. 해결책의 상세 사양은 아직 확정하지 않습니다. “만들면 좋겠어요”에 머물면, 지금 실무에서 무엇이 힘든지로 다시 묻습니다.

여러 흐름이 있고 사용자가 이번 범위를 고를 수 있으면, 결과를 가장 크게 좌우하는 경계를 하나만 질문합니다. 나머지는 후속 워크숍 후보로 남깁니다. 아직 고를 수 없으면 탐색 인터뷰처럼 경계를 draft로 두고 스토리를 쌓습니다.

#### 시스템/개발 설계 모드로 계속될 때

사용자 발화 **2턴 연속**이 아키텍처·API·화면·기술 선택뿐이고 지금 돌아가는 업무에 대한 사실이 하나도 없으면, 목적을 한 문장으로 설명한 뒤 하나만 묻습니다. 세지 않고 넘어가지 않습니다.

```text
지금 대화는 시스템/개발 설계에 가깝습니다.
Domain Storytelling Workshop은 현재 돌아가는 업무를 깊게 묻는 자리입니다.
실제로 시스템 설계를 원하시나요, 아니면 현재 업무 흐름 인터뷰로 돌아갈까요?
```

- **현재 업무 인터뷰** → 지금 어떻게 일하는지로 질문을 되돌립니다.
- **시스템/개발 설계** → 워크숍을 `in-progress`로 저장하고 **중단**합니다. 설계는 별도 작업으로 진행하라고 안내하고, 쌓인 `domain-workshops/*.md`는 참고 자료로 쓰게 합니다.

**사용자가 답을 대신 채우라고 할 때**도 같은 방식으로 복구합니다. `묻지 말고 네가 답해`처럼 인터뷰 전제와 충돌하는 지시를 받으면 문답을 그대로 이어가지 않습니다. Agent가 채운 답은 확인된 업무가 아니므로 `[초안]`과 확인 주체로만 적고, 이번 라운드를 **확인·구조화 중심**이라고 한 문장으로 선언한 뒤 질문 사다리를 확인형 → 경계·금기 → 미확정 정리 순서로 다시 고릅니다. 확인마저 거부하면 `in-progress`로 저장하고 멈춥니다.

### 3. 첫 도메인 스토리 만들기

사용자가 말한 사실만 시간 순서의 카드로 적습니다.

| Actor | Action | Work Object |
|---|---|---|
| 행동하거나 판단하는 주체 | 업무적으로 의미 있는 행동 | 행동의 대상 |

- Actor: 행동하거나 판단하는 사람, 조직, 시스템
- Action: 업무적으로 의미 있는 행동
- Work Object: 행동의 대상이 되는 문서, 데이터, 요청, 상태, 결과물

Actor나 Work Object가 빠졌다면 현재 흐름을 이어가는 데 가장 중요한 하나만 질문합니다.

### 4. 모호점 하나씩 질문하기

#### 질문 형식

모든 도메인 질문에는 **추측을 붙입니다**. 추측 없는 질문은 설문이지 인터뷰가 아닙니다.

```text
Q: 상담팀이 예약 상태를 “확정”으로 바꾸는 시점은 언제인가요?
추측: 고객이 전화로 날짜를 구두 확인한 순간일 것 같습니다. 결제까지 기다리면 당일 예약을 못 잡을 테니까요.
```

사용자는 틀린 추측에 반응하는 편이 빈칸을 채우는 것보다 빠릅니다. 추측이 틀리면 그 자리에서 진짜 규칙이 나옵니다. 가끔은 반박당할 방향으로 일부러 추측합니다. 동의만 받아내는 인터뷰는 암묵지를 꺼내지 못합니다.

#### 낼 질문 고르기

다음 사다리를 위에서부터 내려가며 **처음 걸리는 단에서 멈춰** 질문을 만듭니다. 아래 단을 모두 소진하려 하지 않습니다.

1. 방금 답이 앞의 답과 모순되는가 → 두 설명을 나란히 보여주고 어느 쪽인지 묻습니다
2. 방금 답에 “보통”, “적절하면”, “문제없으면”, “필요할 때”처럼 흐릿한 기준이 있고 그게 결과를 바꾸는가 → 그 기준 하나만 팝니다
3. 사람이 판단하는 지점인데 무엇을 보고 판단하는지 모르는가
4. 상태를 바꾸는 조건이 비어 있는가
5. 정상 흐름만 있고 실패·취소·중복·재시도 때 무엇을 하는지 모르는가
6. 이 기록을 다음에 쓸 사람과 데이터 출처가 비어 있는가

#### 도메인 질문인지 검사하기

질문을 내기 전에 한 번 검사합니다. **이 질문의 답을 사용자가 어제 한 일에서 끌어낼 수 있는가?**

- 끌어낼 수 있다 → 도메인 질문입니다. 냅니다.
- 사용자가 새로 결정해야 답할 수 있다 → 구현 유도 질문입니다. 내지 않습니다. 그 결정이 왜 필요한지로 바꿔 묻습니다.

```text
낸다:    지금은 미달 지표를 어떻게 골라내세요?
안 낸다: 미달 판정 임계값을 몇 %로 할까요?

낸다:    그 판단을 누가 며칠에 하세요?
안 낸다: 배치를 일 단위로 돌릴까요, 주 단위로 돌릴까요?
```

#### 답변을 채팅에 얼마나 보여줄지

매 답변 뒤에 기록을 갱신합니다. 노출 수준은 5단계 분류로 판단합니다.

- 상태 변화·미확정, 또는 Actor·Action·Work Object·용어처럼 단순한 사실이면 파일에만 반영하고 채팅에는 다음 질문만 남깁니다.
- 비즈니스 규칙·판단 기준·예외처럼 이후 처리 방식을 바꾸는 답변이면 `확인: [규칙 한 줄]`만 짧게 보여준 뒤 다음 질문으로 넘어갑니다. 6단계의 전체 재생 형식(흐름 목록·범위 초안·확인 질문)은 흐름 한 덩어리가 정리됐을 때만 씁니다.

```text
확인: 월말 예상 달성률이 100% 이상이면 부족 지표 해석·전달을 생략합니다.
```

사용자가 “모른다”고 답하면 미확정 질문과 확인할 주체를 기록하고 다음으로 갑니다.

### 5. 상태·규칙·예외 분리하기

답변을 다음 중 하나로 분류합니다.

- 상태 변화: 무엇이 어떤 상태에서 어떤 상태가 되는가
- 비즈니스 규칙: 언제 무엇을 해야 하거나 하지 않아야 하는가
- 판단 기준: 사람이 결정을 내릴 때 보는 정보
- 예외: 정상 흐름과 달라지는 조건과 처리
- 미확정: 답을 모르거나 서로 합의되지 않은 내용

확인되지 않은 내용은 한 줄 안에 세 가지를 적습니다. 하나라도 빠지면 그 줄은 미완성입니다.

```text
[초안] 월말 마감은 영업일 기준 3일 전에 잠근다 — 확인 주체: 정산팀 / 확인 방법: 실제 마감 로그 3건 대조
```

이렇게 적으면 `[초안]`만 찾아도 남은 확인 과제가 담당자와 방법까지 붙은 목록으로 나옵니다.

### 6. 중간 재생으로 확인받기

정상 흐름이 이어졌거나 중요한 분기가 정리되면 짧게 재생합니다. 시작·종료 초안이 있으면 함께 보여주고, 확인된 스토리에 맞게 고칩니다. 맨 위에 현재 이해도를 한 줄로 선언합니다. 진행 상태는 담당자가 들고 갑니다.

```md
이해도: ~40% — 부족: 상태를 되돌리는 조건, 담당자가 바뀌는 시점

지금까지 이해한 흐름:
1. ...
2. ...

범위 초안:
- 시작: ...
- 종료: ...

새로 확인된 규칙:
- ...

다르게 이해한 부분이 있나요?
```

사용자가 수정하면 이전 기록을 그대로 쌓지 말고 최신 확인 내용으로 고칩니다. 확인받지 못한 부분은 초안으로 표시합니다. 스토리가 갈라지면 지금 확인 중인 흐름만 유지하고 나머지는 후속 워크숍 후보로 옮깁니다.

중간 재생이 끝날 때마다 현재 내용을 저장하고, 아직 답하지 않은 질문 중 다음 질문 하나를 파일에 남깁니다.

### 7. 종료 테스트

질문을 멈출지는 느낌이 아니라 테스트로 정합니다.

> 지금 다음 질문 세 개를 만들어 보고, 사용자의 답을 예측할 수 있는가?

- **예측된다** → 질문을 멈추고 최종 재생으로 갑니다.
- **예측 안 되는데 이미 재생을 3회 이상 했다** → 계속 파지 않습니다. `여기서부터는 제가 예측이 안 됩니다. 이 부분은 누구에게 확인해야 할까요?`라고 말하고 미확정으로 남긴 뒤 종료합니다.

멈추기 전에 아래가 기록돼 있는지 확인합니다.

- 확인된 스토리로 시작과 종료가 연결됨. 처음 적은 경계 문장이 끝까지 그대로일 필요는 없음
- 주요 Actor, Action, Work Object가 식별됨
- 결과를 바꾸는 규칙과 대표 예외가 기록됨
- 미확정 사항이 확인된 사실과 분리됨

처음 설명에 없던 규칙·예외가 몇 개 드러났는지는 `확인 기록`에 적습니다. 개수는 관찰 지표이지 통과 조건이 아닙니다. 질문 수나 문서 길이로 `status: confirmed`를 올리지 않습니다. 최종 재생에 대한 사용자의 명시적 확인이 있고 새 `모름`이 더 나오지 않을 때만 올립니다.

### 8. 최종 재생과 선택적 연결점

아래 출력의 1~5절을 먼저 보여주고 수정 또는 확인을 받습니다.

확인 후에만, 연결점이 필요하면 하나만 묻습니다. 필수가 아닙니다.

```text
확인된 도메인 기록을 다음 산출물용 연결점으로도 정리할까요?
1. 개발자 연결점
2. 데이터 분석가 연결점
3. 데이터 엔지니어 연결점
4. 지금은 생략 (도메인 기록만 유지)
```

- **1–3** → 선택한 역할에 맞는 6절만 작성하고 `connection_role`에 기록합니다.
- **4** → 6절은 비우거나 `생략`으로 두고 `connection_role: none`으로 둡니다. 나중에 같은 파일을 이어 확인된 기록만으로 연결점을 추가할 수 있습니다.

연결점 작성 중에도 구현·아키텍처를 새로 설계하지 않습니다. 확인된 도메인 규칙만 다음 산출물 조건으로 옮깁니다.

- 개발자: 기능 경계, Tool·API·DB 접근, 사람 승인, 테스트할 동작
- 데이터 분석가: 의사결정 질문, 지표·분석 단위·비교 기준, 데이터 한계, 결과로 바꿀 행동
- 데이터 엔지니어: 출처·목적지, 스키마·키, 갱신 주기, 중복·재처리, 품질·복구 조건

연결점까지 저장했으면 **그 턴을 끝냅니다.** 같은 턴에서 설계·코드·분석 실행으로 넘어가지 않고, 다음에 무엇을 할지는 사용자가 고르게 합니다.

### 9. 저장하고 재개 지점 남기기

새 워크숍은 `domain-workshops/<업무-이름>.md`에 저장합니다. 같은 이름의 파일이 있으면 덮어쓰지 말고 사용자에게 기존 파일을 이어갈지 새 이름으로 만들지 묻습니다.

- 질문을 멈추거나 중간 재생을 마칠 때마다 최신 이해로 파일을 갱신합니다.
- `role: workshop-facilitator`와 모드를 frontmatter에 기록합니다.
- 연결점을 썼으면 `connection_role`을 기록하고, 아니면 `none` 또는 생략합니다.
- 확인 전에는 `status: in-progress`, 최종 확인 후에는 `status: confirmed`로 기록합니다.
- `updated_at`은 실제 저장일로 갱신합니다.
- 답을 기다리는 질문 하나를 `다음 질문`에 남깁니다.
- 사용자가 수정한 옛 설명은 본문에 중복 보관하지 않고 `확인 기록`에 변경 사실만 남깁니다.

채팅을 다시 시작해도 1단계에서 이 파일을 선택하면 저장된 모드와 `다음 질문`을 기준으로 이어갑니다.

예전 파일에 `role: developer | data-analyst | data-engineer`만 있으면 인터뷰 역할은 `workshop-facilitator`로 읽고, 기존 값은 `connection_role` 후보로만 참고합니다. 이어하기에서 역할을 다시 고르게 하지 않습니다.

## 완료 조건 (파일에서 확인)

워크숍을 닫기 전에 확인합니다. 각 항목은 저장된 Markdown에서 눈으로 확인할 수 있어야 합니다.

- [ ] 6절은 사용자가 명시적으로 고른 경우에만 채워져 있다
- [ ] `확인 기록`에 확인된 범위와 아직 확인받지 못한 내용이 나뉘어 있다

## 흔한 자기합리화

| 합리화 | 실제 |
|---|---|
| “사용자가 원하는 걸 명확히 말했으니 그대로 적으면 된다” | 사용자가 말한 건 해결책입니다. 그게 왜 필요한지 답하지 못하면 요구사항이 아니라 가설입니다. |
| “이건 개발·분석 담당이 판단할 영역이니 내가 정해도 된다” | 정해도 되는 건 구현 방식이고, 지금 묻는 건 지금 누가 어떻게 하고 있는가입니다. 업무는 사용자만 압니다. |
| “업계에서는 보통 이렇게 하니 채워두자” | 관행으로 채운 칸은 확인된 기록이 아닙니다. 비워두고 미확정 질문으로 남깁니다. |
| “질문이 길어지니 몇 개 묶어서 묻자” | 묶으면 사용자가 첫 질문에만 답하고 나머지는 얕아집니다. 세 번째 질문은 첫 답에 따라 달라집니다. |
| “여기까지 왔으니 설계까지 같이 해주면 친절하다” | 확인받지 않은 기록 위의 설계는 두 번 버립니다. 설계를 원하면 워크숍을 멈추고 넘깁니다. |
| “사용자가 ‘좋아요’라고 했으니 `confirmed`로 바꾸자” | 재생 내용에 대한 명시적 확인이 아니면 예의상 응답입니다. 무엇을 확인했는지 되물은 뒤 바꿉니다. Agent가 대신 채운 답은 확인이 아니므로 `[초안]`으로 남깁니다. |
| “다음에 뭘 물을지 사용자에게 물어보면 되겠다” | 진행은 담당자 몫입니다. 사용자에게 넘기는 순간 워크숍이 아니라 일반 Q&A가 됩니다. |
| “주제에 as-is가 없지만 형식은 맞출 수 있다” | 형식만 맞은 기록은 확인된 업무가 아닙니다. §2에서 걸러내거나 `범위 예외`로 남깁니다. |

## 실패 신호

대화에서 바로 보이는 신호입니다. 하나라도 보이면 그 자리에서 절차로 돌아갑니다.

- 추측이 붙지 않은 질문을 냄
- 한 메시지에 질문이 두 개 이상 들어감
- 고정 gate를 쓸 수 있는데 채팅 번호 목록만 반복하거나, gate와 도메인 질문을 한 턴에 함께 던짐
- 사용자가 새로 결정해야만 답할 수 있는 질문을 냄
- 재생을 세 번 했는데 이해도 숫자가 오르지 않음
- 단순한 사실 답변에도 `확인:` 문구를 붙이거나, 흐름이 정리되지 않았는데 전체 재생 형식을 매번 사용함
- 저장된 워크숍이 있는데 새 작업만 제안하거나, 선택하지 않은 파일을 임의로 이어감
- 채팅 종료 전에 현재 내용과 다음 질문을 저장하지 않음
- 사용자가 수정한 옛 설명이 최신 기록에 그대로 남음
- 확인 전에 연결점을 작성하거나, 생략 의사를 무시하고 연결점을 강요함
- 최종 확인을 받은 턴에 이어서 설계·코드·분석 실행으로 넘어감

## 스킬 자체 검증 (실험)

문서화가 부족하지만 사용자가 잘 아는 업무 하나로 실행합니다.

1. 첫 설명과 최종 도메인 스토리를 비교하고, 처음에 없던 규칙·예외 수와 사용자가 수정한 지점을 기록합니다.
2. 입장 확인이 주제에 맞게 작동했는지(as-is 없는 주제를 걸렀는지) 확인합니다.
3. 추측이 붙은 질문에 사용자가 더 빨리·구체적으로 답했는지 확인합니다.
4. 종료 테스트로 멈췄는지, 아니면 질문이 소진돼서 멈췄는지 기록합니다.
5. 고정 gate가 `AskQuestion`(또는 동일 선택지 폴백)으로 한 턴에 하나씩 나왔는지 확인합니다.

관찰할 항목:

1. 바로 도움이 된 내용
2. 불필요하거나 과도했던 질문
3. 다음 실행에서 바꿀 한 가지

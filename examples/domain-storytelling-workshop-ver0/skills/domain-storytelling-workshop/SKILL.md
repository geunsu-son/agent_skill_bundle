# Domain Storytelling Workshop

## 상태

`ver0` draft. 실제 업무 워크숍으로 질문 순서와 출력 형식을 검증할 예정입니다.

## 목적

사용자의 업무 설명에서 빠진 행위자, 행동, 업무 대상, 조건, 예외와 판단 기준을 대화로 드러내고, 확인된 내용을 개발에 재사용할 수 있는 도메인 기록으로 만듭니다.

## 개발담당자의 마인드

**사용자가 요청한 해결책을 그대로 만드는 것이 아니라, 그 요청 뒤의 문제를 확인한다.**

- “CRM을 만들어 달라”, “버튼을 추가해 달라” 같은 요청은 확정 요구사항이 아니라 **해결책 가설**로 기록합니다.
- 누가 어떤 상황에서 무엇이 불편한지, 현재 어떻게 우회하는지, 어떤 결과가 달라져야 하는지를 먼저 확인합니다.
- 문제가 확인되면 개발담당자가 가능한 해결책과 trade-off를 제시하고 설계를 주도하며, 사용자는 도메인 적합성을 검증합니다.
- 설계 주도권을 사용자 의견을 무시하거나 확인되지 않은 문제를 대신 만들어도 된다는 뜻으로 해석하지 않습니다.

## 사용 시점

- 문서화되지 않은 업무를 기능이나 Agent 요구사항으로 바꾸기 전
- 같은 기능의 수정 요청이 반복되지만 업무 규칙이 불명확할 때
- 기존 코드·데이터 처리 절차가 어떤 업무 규칙을 구현하는지 복원할 때

해결책이나 구현만 요청받았더라도 핵심 업무 규칙이 불명확해 결과가 달라질 수 있으면 먼저 사용합니다.

## 관련 Rule

- [`rules/domain-storytelling-workshop.mdc`](../../rules/domain-storytelling-workshop.mdc)

## 입력

- 문서화할 업무 흐름의 이름 또는 첫 설명
- 이 흐름을 정리하려는 이유와 이후 사용할 사람
- 있으면: 기존 문서, 화면, 코드, 데이터 정의

첫 설명만 있어도 시작합니다. 필요한 정보를 체크리스트로 한꺼번에 요구하지 않습니다.

## 절차

### 1. 워크숍 경계 잡기

사용자의 첫 설명에서 시작 사건과 원하는 종료 결과를 한 문장으로 임시 정리합니다.

```text
[시작 사건]이 발생하면, [종료 결과]가 될 때까지의 흐름을 다룹니다.
```

사용자가 해결책을 요청했다면 다음 두 항목을 분리합니다.

- 해결하려는 문제: 불편을 겪는 Actor, 상황, 현재 우회 방법, 바뀌어야 할 결과
- 요청한 해결책 가설: 사용자가 제안한 기능·도구·방식

문제가 드러나지 않았다면 “그 해결책이 없어서 현재 어떤 불편이 생기나요?”처럼 가장 중요한 질문 하나만 묻습니다. 해결책의 상세 사양은 아직 확정하지 않습니다.

업무가 여러 흐름을 포함하면 결과를 가장 크게 좌우하는 경계를 하나만 질문합니다. 사용자가 고르면 나머지는 후속 워크숍 후보로 남깁니다.

### 2. 첫 도메인 스토리 만들기

사용자가 말한 사실만 시간 순서의 카드로 적습니다.

| Actor | Action | Work Object |
|---|---|---|
| 행동하거나 판단하는 주체 | 업무적으로 의미 있는 행동 | 행동의 대상 |

- Actor: 행동하거나 판단하는 사람, 조직, 시스템
- Action: 업무적으로 의미 있는 행동
- Work Object: 행동의 대상이 되는 문서, 데이터, 요청, 상태, 결과물

Actor나 Work Object가 빠졌다면 현재 흐름을 이어가는 데 가장 중요한 하나만 질문합니다.

### 3. 모호점 하나씩 질문하기

매 답변 뒤에 기록을 갱신하고 다음 질문 하나를 고릅니다. 우선순위는 다음과 같습니다.

1. 서로 모순되거나 흐름을 바꾸는 설명
2. 시작·종료 또는 책임 주체가 불명확한 지점
3. 상태를 바꾸는 조건과 사람이 판단하는 기준
4. 실패·취소·중복·재시도 같은 예외
5. 데이터 출처와 결과 사용자

낮은 우선순위 질문을 모두 소진하려 하지 않습니다. 사용자가 “모른다”고 답하면 미확정 질문과 확인할 주체를 기록하고 다음으로 갑니다.

질문 예:

```text
예약 상태를 바꾸는 조건이 아직 모호합니다. 상담팀은 어떤 정보가 확인되면 상태를 바꾸나요?
```

### 4. 상태·규칙·예외 분리하기

답변을 다음 중 하나로 분류합니다.

- 상태 변화: 무엇이 어떤 상태에서 어떤 상태가 되는가
- 비즈니스 규칙: 언제 무엇을 해야 하거나 하지 않아야 하는가
- 판단 기준: 사람이 결정을 내릴 때 보는 정보
- 예외: 정상 흐름과 달라지는 조건과 처리
- 미확정: 답을 모르거나 서로 합의되지 않은 내용

“보통”, “적절하면”, “문제없으면”, “필요할 때” 같은 표현은 결과를 바꾸는 기준일 때만 한 단계 더 질문합니다.

### 5. 중간 재생으로 확인받기

정상 흐름이 이어졌거나 중요한 분기가 정리되면 짧게 재생합니다.

```md
지금까지 이해한 흐름:
1. ...
2. ...

새로 확인된 규칙:
- ...

다르게 이해한 부분이 있나요?
```

사용자가 수정하면 이전 기록을 그대로 쌓지 말고 최신 확인 내용으로 고칩니다. 확인받지 못한 부분은 초안으로 표시합니다.

### 6. 워크숍 종료 판단

다음을 만족하면 질문을 멈추고 정리 단계로 갑니다.

- 시작과 종료가 연결된 도메인 스토리 1개가 있음
- 주요 Actor, Action, Work Object가 식별됨
- 결과를 바꾸는 규칙과 대표 예외가 기록됨
- 미확정 사항이 확인된 사실과 분리됨

처음 설명에 없던 규칙 또는 예외 3개를 찾는 것을 실험 목표로 삼되, 수를 채우려고 내용을 만들지 않습니다. 더 없다는 사용자 확인도 결과로 기록합니다.

### 7. 최종 재생과 개발 연결

아래 출력의 1~5절을 먼저 보여주고 수정 또는 확인을 받습니다. 확인 후에만 6절의 개발 연결점을 작성합니다.

개발 연결점에는 다음만 포함합니다.

- 필요한 데이터와 출처
- 필요한 Agent Tool, API, DB 접근 후보
- 사람이 승인해야 하는 작업
- 자동화 가능한 작업
- 테스트해야 할 확인된 도메인 규칙

구체적인 아키텍처나 구현은 별도 요청이 있을 때 후속 작업으로 둡니다.

## 출력 형식

```md
# [업무 이름] 도메인 기록

## 1. 범위

- 해결하려는 문제:
- 요청한 해결책 가설:
- 시작 사건:
- 종료 결과:
- 이번에 포함하지 않은 흐름:

## 2. 도메인 스토리

| 순서 | Actor | Action | Work Object |
|---|---|---|---|
| 1 |  |  |  |

## 3. 도메인 용어집

| 용어 | 확인된 의미 | 혼동 주의 |
|---|---|---|

## 4. 비즈니스 규칙과 상태 변화

- [확인됨] 조건 → 행동 또는 상태 변화
- [초안] 확인이 더 필요한 규칙

## 5. 예외 시나리오와 미확정 질문

### 예외
- 조건 → 처리 → 다음 상태

### 미확정 질문
- 질문 / 확인할 주체

## 6. 개발 연결점

- 필요한 데이터와 출처:
- Tool / API / DB 접근 후보:
- 사람 승인 지점:
- 자동화 후보:
- 테스트할 도메인 규칙:

## 확인 기록

- 사용자가 확인한 범위:
- 수정되거나 거절된 내용:
- 아직 확인받지 못한 내용:
```

## 완료 조건

- 해결하려는 문제와 요청한 해결책 가설이 구분됨
- 도메인 스토리의 시작과 종료가 연결됨
- Actor, Action, Work Object가 실제 사용자 표현에 근거함
- 규칙, 예외, 미확정 질문이 서로 구분됨
- 모순이 해소되었거나 미확정으로 남음
- 최종 기록의 확인 여부가 명시됨
- 확인 후에만 개발 연결점이 작성됨

## 실패로 보는 결과

- 사용자가 요청한 기능이나 도구를 문제 확인 없이 확정 요구사항으로 취급함
- 첫 설명 뒤 바로 해결책이나 코드를 제시함
- 여러 질문을 한꺼번에 던져 사용자가 답할 우선순위를 잃음
- 업계 관행이나 Agent의 추정을 확인된 규칙으로 기록함
- 정상 흐름만 있고 예외나 사람 판단 지점을 확인하지 않음
- 사용자가 수정한 옛 설명이 최신 기록에 그대로 남음
- 확인받지 않은 기록을 확정 요구사항으로 표현함

## 검증 방법

문서화가 부족하지만 사용자가 잘 아는 업무 하나로 실행합니다.

1. 첫 설명과 최종 도메인 스토리를 비교합니다.
2. 처음에 없던 규칙 또는 예외가 몇 개 드러났는지 기록합니다.
3. 사용자가 잘못 이해했다고 수정한 횟수와 지점을 기록합니다.
4. 개발자가 규칙을 테스트 조건으로 바꿀 수 있는지 확인합니다.

관찰할 항목:

1. 바로 도움이 된 내용
2. 불필요하거나 과도했던 질문
3. 다음 실행에서 바꿀 한 가지

## 향후 Script·Automation 후보

없습니다. 현재 핵심은 대화의 판단과 확인이며, 반복되는 결정론적 변환이나 실행 조건은 아직 관찰되지 않았습니다.

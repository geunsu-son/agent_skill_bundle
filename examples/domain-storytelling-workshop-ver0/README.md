# Domain Storytelling Workshop — ver0 Example

Agent를 **워크숍 담당자**로 두고, 사용자의 **현재 업무·운영** 설명에서 암묵적인 조건·예외·용어·판단 기준을 질문해 다음 작업에 재사용할 도메인 기록으로 만드는 예시입니다.

완성된 요구사항 분석 프레임워크가 아닙니다. 개발/시스템 설계 워크숍도 아닙니다. Rule과 대화형 Skill을 다른 저장소의 실제 업무에 시험하는 `testing` 예시입니다.

## 해결하려는 문제

“예약 상태를 바꾼다”, “퍼널을 분석한다”, “데이터를 정제해 적재한다” 같은 설명은 구현 방향을 잡기에는 부족합니다. 그런데 Agent가 바로 코드로 넘어가면 다음이 뒤늦게 드러납니다.

- 누가 어떤 사건으로 작업을 시작하는가
- 어떤 조건과 판단으로 상태가 바뀌는가
- 중복·취소·실패 때 무엇을 하는가
- 어떤 데이터가 필요하고 결과를 누가 사용하는가
- 사람이 반드시 승인해야 하는 지점은 어디인가

이 예시는 그 공백을 한 번에 하나씩 질문하고, 사용자가 확인한 내용만 (원할 때) 다음 작업의 연결점으로 옮깁니다. 주제만 있는 인터뷰로 시작해도 됩니다. 시작·종료 경계는 세션 중 draft로 갱신합니다.

다만 **지금 아무도 하고 있지 않은 일**(앞으로 만들 시스템·봇)은 복원할 암묵지가 없어 이 워크숍에 맞지 않습니다. Skill이 입장에서 한 문항으로 확인합니다.

## 상태

`testing` — Bundle Catalog에서 선택 설치할 수 있습니다. 입장 확인, 질문 형식(가설·추측), 종료 테스트, Markdown 저장·재개와 출력 형식은 다른 저장소의 실제 워크숍으로 검증하고 관찰을 Issue로 되돌립니다.

## 구성

```text
Rule
→ 워크숍 담당자, 추측을 붙인 한 질문씩 진행, 사실·가정 분리, 확인 전 구현 금지

Skill
→ 새 작업/이어하기 → 입장 확인(as-is) → 모드 → 경계 draft → 스토리 → 재생·확인 → (선택) 연결점
```

- [`rules/domain-storytelling-workshop.mdc`](rules/domain-storytelling-workshop.mdc)
- [`skills/domain-storytelling-workshop/SKILL.md`](skills/domain-storytelling-workshop/SKILL.md)
- 작업 정의: [`workshop/domain-storytelling-workshop.md`](../../workshop/domain-storytelling-workshop.md)

Script와 Automation은 아직 두지 않습니다. 저장된 Markdown의 필수 항목을 검사하는 `validate-workshop-md`만 후보로 적어 뒀고, 같은 확인이 한 번 더 반복되면 구현합니다. 진행 결과는 소비 프로젝트의 `domain-workshops/*.md`에 저장합니다.

## 사용 예시

```text
domain-storytelling-workshop을 시작해줘.
```

주제만 있어도 됩니다.

```text
이 업무에서 지표를 어떻게 보고 해석하는지 인터뷰로 남겨줘.
```

Skill을 호출하면 저장된 파일이 있을 때만 `새 워크숍 / 기존 워크숍 이어하기`를 묻습니다. 새 워크숍에서는 as-is가 있는지 한 문항으로 확인한 뒤, 목적이 분명하지 않으면 모드를 확인합니다.

- **탐색 인터뷰(문서화):** 주제만으로 시작. 첫 질문은 흐름 후보 선택이 아니라 누가·무엇을·어떤 결과로 보는지 한 줄 인터뷰. 시작·종료는 draft로 두고 중간 재생마다 수정.
- **구현 전 정리:** 문제·니즈와 해결책 가설을 분리하고, 이번에 다룰 흐름을 초기에 더 분명히. 해결책 가설은 구현 결정으로 굽지 않음.
- **설계 모드 지속 시:** 사용자 발화 2턴 연속이 설계·기술 선택뿐이면 목적을 안내하고, 시스템 설계를 원하면 워크숍을 중단하고 쌓인 문서는 참고 자료로 둠.

인터뷰 동안 Agent는 항상 **워크숍 담당자**입니다. 도메인 질문에는 Agent의 추측이 함께 붙습니다. 틀린 추측에 반박하는 편이 빈칸을 채우는 것보다 빠르기 때문입니다.

```text
Q: 상담팀이 예약 상태를 “확정”으로 바꾸는 시점은 언제인가요?
추측: 고객이 전화로 날짜를 구두 확인한 순간일 것 같습니다. 결제까지 기다리면 당일 예약을 못 잡을 테니까요.
```

이어하기를 선택하면 파일의 모드와 `다음 질문`을 사용합니다. Skill은 호출됐을 때 gate를 실행하며 모든 새 채팅에서 자동 시작되지는 않습니다.

## 연결점 (확인 후·선택)

도메인 기록(1–5절)을 사용자가 확인한 뒤에만, 원할 때 연결 역할을 하나 고릅니다. 생략해도 됩니다.

| 연결 역할 | 확인된 규칙을 옮기는 항목 |
|---|---|
| 개발자 | 기능 경계, Tool·API·DB, 승인, 테스트할 동작 |
| 데이터 분석가 | 의사결정, 지표, 분석 단위, 비교, 데이터 한계, 후속 행동 |
| 데이터 엔지니어 | 출처·목적지, 스키마·키, 갱신, 중복·재처리, 품질·복구 |
| 생략 | 도메인 기록만 유지 |

공통 도메인 스토리는 하나이며 역할별 Skill을 복제하지 않습니다. Agent는 인터뷰 중 역할별 질문 목록을 제시하지 않고, 현재 결과를 가장 크게 바꿀 도메인 질문 하나만 묻습니다.

## 최종 산출물

1. 범위와 시작·종료
2. `Actor → Action → Work Object` 도메인 스토리
3. 도메인 용어집
4. 비즈니스 규칙과 상태 변화
5. 예외 시나리오와 미확정 질문
6. (선택) 확인 후 작성한 연결점
7. 다음 채팅에서 이어갈 질문

결과 파일은 `role: workshop-facilitator`, 모드, 진행 상태, 수정일, (있으면) `connection_role`을 frontmatter에 기록합니다. 시작·종료는 확인 전까지 `draft`로 둡니다. 구체적인 아키텍처, 분석 실행이나 파이프라인 구현은 별도 후속 작업입니다.

## 작은 실험

문서화가 부족하지만 사용자가 잘 아는 업무 하나를 선택해 실행합니다. 세션 중 확인할 통과·실패 기준과 실행 후 관찰 항목은 Skill 하나에만 둡니다. 여기서 다시 나열하지 않습니다.

- 세션 중 확인: Skill의 「완료 조건 (파일에서 확인)」
- 어긋났을 때의 신호: Skill의 「실패 신호」, 「흔한 자기합리화」
- 실행 후 관찰: Skill의 「스킬 자체 검증 (실험)」

관찰 결과는 `report-bundle-feedback`으로 Issue에 되돌리고, 그 Issue를 근거로만 이 예시를 고칩니다.

## ver0에서 일부러 하지 않은 것

- 도메인 스토리 카드용 UI
- PRD·데이터 모델·API 문서 자동 생성
- 도메인별 질문 백과사전
- Script·Automation
- `.cursor/` 정식 번들 승격

> 이 예시는 Agent가 일반적인 업무 절차를 대신 채우는 도구가 아니라, 사용자가 가진 도메인 지식을 개발 전에 명시적으로 확인하기 위한 보조 도구입니다.

# Domain Storytelling Workshop — ver0 Example

Agent를 **선택한 담당자이자 워크숍 진행자**로 두고, 사용자의 업무 설명에서 암묵적인 조건·예외·용어·판단 기준을 질문해 다음 작업에 재사용할 도메인 기록으로 만드는 예시입니다.

완성된 요구사항 분석 프레임워크가 아닙니다. Rule과 대화형 Skill을 실제 업무 하나에 시험하기 위한 `draft`입니다.

## 해결하려는 문제

“예약 상태를 바꾼다”, “퍼널을 분석한다”, “데이터를 정제해 적재한다” 같은 설명은 구현 방향을 잡기에는 부족합니다. 그런데 Agent가 바로 코드로 넘어가면 다음이 뒤늦게 드러납니다.

- 누가 어떤 사건으로 작업을 시작하는가
- 어떤 조건과 판단으로 상태가 바뀌는가
- 중복·취소·실패 때 무엇을 하는가
- 어떤 데이터가 필요하고 결과를 누가 사용하는가
- 사람이 반드시 승인해야 하는 지점은 어디인가

이 예시는 구현 전에 그 공백을 한 번에 하나씩 질문하고, 사용자가 확인한 내용만 요구사항 후보로 연결합니다.

## 상태

`draft` — 참고자료를 바탕으로 Rule·Skill 최소 구조만 만들었습니다. 실제 워크숍으로 질문 순서와 출력 형식을 검증하지 않았습니다.

## 구성

```text
Rule
→ 역할, 한 질문씩 진행, 사실·가정 분리, 확인 전 구현 금지

Skill
→ 새 작업/이어하기 → 담당자 선택 → 범위 → 스토리 → 재생·확인 → 담당자 연결
```

- [`rules/domain-storytelling-workshop.mdc`](rules/domain-storytelling-workshop.mdc)
- [`skills/domain-storytelling-workshop/SKILL.md`](skills/domain-storytelling-workshop/SKILL.md)
- 작업 정의: [`workshop/domain-storytelling-workshop.md`](../../workshop/domain-storytelling-workshop.md)

Script와 Automation은 두지 않습니다. 현재 핵심은 대화 중 모호점의 우선순위를 판단하고 사용자에게 확인받는 일입니다. 진행 결과는 소비 프로젝트의 `domain-workshops/*.md`에 저장합니다.

## 사용 예시

```text
domain-storytelling-workshop을 시작해줘.
```

Skill을 호출하면 저장된 파일이 있을 때만 `새 워크숍 / 기존 워크숍 이어하기`를 묻습니다. 새 워크숍에서는 다음 담당자를 선택합니다.

1. 개발자
2. 데이터 분석가
3. 데이터 엔지니어
4. 아직 모르겠음

`아직 모르겠음`은 담당자 역할이 아닙니다. 공통 질문으로 문제와 가장 먼저 필요한 결과물을 파악한 뒤 세 담당자 중 하나를 추천하고 확인받습니다.

이어하기를 선택하면 파일의 담당자와 `다음 질문`을 사용합니다. Skill은 호출됐을 때 gate를 실행하며 모든 새 채팅에서 자동 시작되지는 않습니다.

## 담당자별 관점

| 담당자 | 워크숍에서 우선 확인할 내용 |
|---|---|
| 개발자 | 기능 경계, 상태, 연동·권한, 승인, 테스트 |
| 데이터 분석가 | 의사결정, 지표, 분석 단위, 비교, 데이터 한계, 후속 행동 |
| 데이터 엔지니어 | 출처·목적지, 스키마·키, 갱신, 중복·재처리, 품질·복구 |

공통 도메인 스토리는 하나이며 역할별 Skill을 복제하지 않습니다. Agent는 역할별 질문 목록을 한꺼번에 제시하지 않고 현재 결과를 가장 크게 바꿀 질문 하나만 묻습니다.

## 최종 산출물

1. 범위와 시작·종료
2. `Actor → Action → Work Object` 도메인 스토리
3. 도메인 용어집
4. 비즈니스 규칙과 상태 변화
5. 예외 시나리오와 미확정 질문
6. 확인 후 작성한 담당자별 연결점
7. 다음 채팅에서 이어갈 질문

결과 파일은 담당자, 진행 상태와 수정일을 frontmatter에 기록합니다. 구체적인 아키텍처, 분석 실행이나 파이프라인 구현은 별도 후속 작업입니다.

## 작은 실험

문서화가 부족하지만 사용자가 잘 아는 업무 하나를 선택합니다.

통과:

- 시작과 종료가 있는 도메인 스토리 1개를 사용자가 확인함
- `아직 모르겠음`으로 시작해도 세 담당자 중 하나가 근거와 함께 확정됨
- 중단 시점의 내용과 다음 질문이 Markdown에 저장됨
- 처음 설명에 없던 규칙 또는 예외 3개 이상을 발견하거나 더 없음을 확인함
- 미확정 내용이 사실과 분리됨
- 선택한 담당자가 확인된 기록을 다음 산출물의 조건으로 바꿀 수 있음

실패:

- 첫 설명 뒤 바로 설계나 코드를 제안함
- `아직 모르겠음`을 담당자로 저장함
- 이어갈 파일을 Agent가 임의로 선택함
- 여러 질문을 한꺼번에 던짐
- 추정한 예외를 실제 규칙처럼 기록함
- 사용자 확인 없이 확정 요구사항이라고 표현함

실행 후 기록:

1. 바로 도움이 된 내용
2. 불필요하거나 과도했던 질문
3. 다음 실행에서 바꿀 한 가지

## ver0에서 일부러 하지 않은 것

- 도메인 스토리 카드용 UI
- PRD·데이터 모델·API 문서 자동 생성
- 도메인별 질문 백과사전
- Script·Automation
- `.cursor/` 정식 번들 승격

> 이 예시는 Agent가 일반적인 업무 절차를 대신 채우는 도구가 아니라, 사용자가 가진 도메인 지식을 개발 전에 명시적으로 확인하기 위한 보조 도구입니다.

# Idea to Agent Artifact

## 사용 시점

다음과 같은 요청에 사용한다.

- 새로운 Agent 작업 아이디어를 저장소에 정리할 때
- 기존 업무를 Rule과 Skill로 분해할 때
- 반복 업무의 최소 구현 예시를 만들 때
- 검증 중인 예시를 재사용 가능한 형태로 다듬을 때

## 목표

아이디어를 과도하게 확장하지 않고, 사용자가 실제로 해결하려는 문제와 기대 결과를 먼저 정의한 뒤 시험 가능한 가장 작은 Agent 산출물로 만든다.

## 절차

### 1. 제공된 정보 확인

먼저 현재 요청과 기존 문서에서 다음 정보가 이미 제공되었는지 확인한다.

- Agent에게 맡길 작업
- 해결하려는 문제
- 기대하는 최종 결과물
- 현재 수행 방식과 불편한 점
- 실행 시점 또는 조건
- 판단 기준과 제약
- 완료 조건

이미 제공된 정보는 다시 질문하지 않는다.

### 2. 작업 아이디어 인터뷰

구현에 필요한 핵심 정보가 부족할 때만 짧은 인터뷰를 수행한다.

#### 최소 필수 질문

다음 세 가지가 불명확하면 구현에 가장 큰 영향을 주는 질문부터 하나씩 확인한다.

1. Agent에게 어떤 작업을 맡기려는가?
2. 최종적으로 어떤 결과물이 나와야 하는가?
3. 현재 방식에서 해결하려는 가장 큰 문제는 무엇인가?

#### 조건부 질문

작업 성격에 따라 필요한 항목만 질문한다.

| 상황 | 확인할 내용 |
|---|---|
| 반복 업무 | 언제, 얼마나 자주 실행하는가? |
| 판단 업무 | 어떤 정보와 기준으로 판단하는가? |
| 자동화 업무 | 어떤 조건에서 시작·중단하는가? |
| 위험하거나 권한이 필요한 작업 | 반드시 지킬 제약과 금지사항은 무엇인가? |
| 결과물 생성 | 대상 독자, 형식, 저장 위치는 무엇인가? |
| 기존 프로세스 대체 | 현재 절차 중 유지해야 할 부분은 무엇인가? |
| 품질 검증 필요 | 완료와 실패를 어떻게 판단하는가? |

#### 질문 방식

- 질문을 한꺼번에 나열하지 않는다.
- 구현 범위에 가장 큰 영향을 주는 질문부터 묻는다.
- 선택지가 명확하면 구체적인 선택지를 함께 제시한다.
- 사용자가 답하기 어려운 세부사항은 합리적인 기본값을 제안한다.
- 사소한 공백은 가정으로 명시하고 구현을 계속한다.

#### 인터뷰 종료 조건

다음 조건을 충족하면 추가 질문을 중단한다.

- 작업 목적을 한두 문장으로 정리할 수 있다.
- Agent의 최종 출력 또는 행동이 구체적이다.
- 최소 구현 범위를 결정할 수 있다.
- 남은 불확실성을 가정이나 실험 항목으로 기록할 수 있다.

### 3. 작업 아이디어 정의

인터뷰 결과를 다음 형식으로 정리한다.

```md
# 작업 아이디어 정의

## 작업 이름

## 해결하려는 문제

## Agent가 수행할 작업

## 기대 결과물

## 현재 방식과 불편한 점

## 실행 시점 또는 조건

## 판단 기준과 제약

## 완료 조건

## 가정과 아직 결정하지 못한 점
```

모든 항목을 억지로 채우지 않는다. 해당 작업에 의미 있는 항목만 작성한다.

### 4. 기존 자료 확인

- `README.md`, `docs/`, `examples/`, `workshop/`을 확인한다.
- 유사한 Rule, Skill, Script, Automation이 있는지 찾는다.
- 기존 예시를 확장할지 새 예시를 만들지 결정한다.

### 5. 구성 요소 분해

정의된 작업 아이디어를 다음 기준으로 나눈다.

- 지속적으로 지킬 판단 기준과 제약 → Rule
- 특정 업무의 단계, 도구, 템플릿, 완료 조건 → Skill
- 반복 가능하고 결정론적인 실행 로직 → Script
- 실행 시각, 주기, 조건 → Automation
- 아직 결정하지 못한 질문과 실험 항목 → Workshop note 또는 observations

불필요한 구성 요소는 만들지 않는다.

### 6. 상태 결정

다음 중 하나로 상태를 정한다.

- `idea`: 생각만 기록된 상태
- `draft`: 최소 구조가 작성된 상태
- `testing`: 실제 사용하며 검증 중인 상태
- `reusable`: 반복 사용으로 재사용 가치가 확인된 상태
- `archived`: 현재는 사용하지 않지만 기록을 남기는 상태

새 아이디어의 기본 상태는 `draft` 이하로 둔다.

### 7. 최소 구현

검증에 필요한 최소 파일만 만든다.

```text
examples/<example-name>/
├── README.md
├── rules/
├── skills/
└── automation.md   # 필요한 경우
```

코드가 아직 필요하지 않다면 빈 `scripts/` 디렉터리를 억지로 만들지 않는다.

### 8. Rule 작성

- 역할, 권한, 제약, 공통 품질 기준만 작성한다.
- 짧고 관찰 가능한 행동 기준을 사용한다.
- 상세 절차와 긴 코드 전문은 넣지 않는다.
- 필요한 경우 금지 패턴을 함께 작성한다.

### 9. Skill 작성

- 사용 시점과 목표를 명확히 적는다.
- Agent가 실행할 수 있는 순서로 단계를 작성한다.
- 입력, 사용하는 도구, 출력 형식, 완료 조건을 포함한다.
- 판단이 필요한 단계와 결정론적 실행 단계를 구분한다.

### 10. Script 후보 판단

다음 조건에 해당하면 Script 분리를 고려한다.

- 같은 코드나 쿼리를 두 번 이상 작성하게 됨
- 입력과 출력이 명확함
- Agent의 해석보다 정확한 반복 실행이 중요함
- 별도 테스트가 필요함

아직 코드화 이점이 불명확하면 후보로만 기록한다.

### 11. 검증 방법 작성

- 예시를 어떻게 실행하거나 호출할지 적는다.
- 좋은 결과와 실패 결과를 구분할 기준을 정한다.
- 실제 사용 후 기록할 관찰 항목을 남긴다.

기본 관찰 항목:

1. 바로 도움이 된 내용
2. 불필요하거나 과도했던 내용
3. 다음 실행에서 바꿀 한 가지

### 12. 연결과 요약

- 관련 README에 새 문서 링크를 추가한다.
- 생성·수정한 파일을 요약한다.
- 현재 미완성인 부분과 다음 실험 항목을 명시한다.

## 완료 조건

- Agent 작업 아이디어의 목적과 기대 결과물이 명확하다.
- 필요한 경우 인터뷰 결과가 작업 아이디어 정의로 정리되어 있다.
- Rule, Skill, Script, Automation의 책임이 중복되지 않는다.
- 최소 한 가지 실행 또는 검증 방법이 있다.
- 현재 상태와 다음 작업이 명시되어 있다.
- README 또는 상위 문서에서 결과물에 접근할 수 있다.

## 기본 요청 예시

```text
이 Agent 작업 아이디어를 공방 규칙에 맞춰 구체화해줘.
이미 설명한 내용은 다시 묻지 말고, 구현에 꼭 필요한 정보만 짧게 확인한 뒤
Rule·Skill·Script·Automation으로 필요한 만큼만 분해해서
실제로 시험할 수 있는 최소 예시를 만들어줘.
```

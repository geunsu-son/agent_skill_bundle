# 작업 아이디어 정의

## 작업 이름

MCP 서버 제작 가이드 (manager rule + 구축 작업 skill)

## 해결하려는 문제

Agent에게 MCP 서버를 맡기면 다음이 반복된다.

- hello-world 템플릿이나 백엔드 API 1:1 래핑으로 바로 들어감
- 개인 클라우드 키가 막혀 있는데도 클라이언트에 키를 요구함
- 호출자 신원과 워크로드 신원을 섞음
- 시크릿을 저장소·로그에 넣거나 연결 확인 없이 완성으로 말함

## Agent가 수행할 작업

범위 정의 → 호출자·워크로드 인증 → 도구 구현 → 연결·검증 순으로 안내·구현한다.

## 기대 결과물

- Rule: 작업 표면, 공유 서버 여부, 두 겹 신원, 전송·품질 원칙
- Skill: 범위, 인증, 도구 구현, 연결·검증 + 오케스트레이션

## 참고 서버에서 README로 확인한 사실

`purple-context-mcp` (전체 소스 대신 README만):

- 데이터: 팀 공유 검색 백엔드. 도구 `retrieve` 하나. GWS는 데이터가 아니라 **호출자 게이트**
- 공유 서버 이유: 개인 IAM MFA·IP 제한, 클라우드 계정 없는 구성원
- 워크로드 신원: 클러스터 역할(IRSA). 클라이언트는 클라우드 키를 들지 않음
- 전송: Streamable HTTP, stateless `POST /mcp`
- 공유 정적 토큰 없음. 401 vs 403, 부팅 시 인증 설정 강제

초안에 있던 “GWS 데이터를 GCP 자격 증명으로 연다 / Drive 도구 여러 개 / Cloud Run”은 README와 맞지 않아 폐기했다.

## 판단 기준과 제약

- Agent 작업 표면. 백엔드 API 전체를 옮기지 않는다
- 호출자 신원과 워크로드 신원을 나눈다
- 시크릿·토큰을 코드·git·로그에 넣지 않는다
- 연결·권한 스모크 없이 완료하지 않는다

## 완료 조건

- 목적에 맞는 최소 도구 표면
- 두 겹 신원이 도구 권한과 맞음
- 클라이언트가 도구를 나열하고 읽기 1건을 성공함

## 가정과 아직 결정하지 못한 점

- 언어/SDK는 고정하지 않는다
- 로컬은 stdio, 팀 공유는 Streamable HTTP
- 어드민 명단·감사 Mongo 스키마는 이 예시의 공통 Skill로 올리지 않는다
- SDK 파일 구조는 README만으로는 미확인
- `.cursor/` 승격·실제 서버 구현은 하지 않는다

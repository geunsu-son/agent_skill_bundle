# 작업 아이디어 정의

## 작업 이름

MCP 서버 제작 가이드 (manager rule + 구축 작업 skill)

## 해결하려는 문제

Agent에게 MCP 서버를 맡기면 다음이 반복된다.

- hello-world 템플릿이나 Google API 메서드 1:1 래핑으로 바로 들어감
- 도구·리소스·프롬프트 구분이 없고, Agent가 실제로 쓸 작업 표면이 설계되지 않음
- GWS/GCP 자격 증명·최소 권한·위임 범위를 코드보다 나중에 붙임
- 시크릿을 저장소·로그·예시 출력에 넣거나, 연결 확인 없이 완성으로 말함

사내 참고: `purple-context-mcp` (GWS + GCP 권한·자격 증명으로 서버를 열고 Agent에 컨텍스트를 제공). 이 환경에서는 저장소가 비공개라 코드를 대조하지 못했다.

## Agent가 수행할 작업

MCP 서버를 만들거나 기존 서버를 확장할 때, manager rule의 판단 기준을 지키고, 범위 정의 → (GWS/GCP면) 권한·자격 증명 → 도구 구현 → 연결·검증 순으로 안내·구현한다.

## 기대 결과물

- Rule: MCP 서버를 설계·구현할 때 계속 지킬 역할·권한·품질 원칙
- Skill: 구축에 반복되는 작업(범위, GCP/GWS 인증, 도구 구현, 연결·검증)과 이를 묶는 오케스트레이션

## 현재 방식과 불편한 점

개발팀이 GCP 권한과 자격 증명으로 서버를 열 수 있는 사례는 있으나, Agent가 같은 기준으로 다음 서버를 만들도록 공방 산출물이 없다.

## 실행 시점 또는 조건

MCP 서버를 새로 만들거나, 기존 서버에 도구·권한·배포를 추가할 때.

## 판단 기준과 제약

- Agent 작업 표면을 만들고, 백엔드 API 전체를 옮기지 않는다.
- 자격 증명·개인정보를 코드·git·로그에 넣지 않는다.
- 쓰기·관리자 권한과 도메인 위임은 명시된 범위만.
- 연결·권한 스모크 테스트 없이 완료하지 않는다.

## 완료 조건

- 목적에 맞는 최소 도구 표면이 정의됨
- 인증·권한이 도구 범위와 맞음
- 클라이언트가 도구를 나열하고 읽기 호출 1건을 성공함
- 한계·가정·하지 않은 범위가 기록됨

## 가정과 아직 결정하지 못한 점

- 가정: 사내 1순위 경로는 GWS 컨텍스트 + GCP 자격 증명. 다른 백엔드에도 같은 원칙을 적용한다.
- 가정: 언어/SDK는 고정하지 않는다. TypeScript 공식 SDK와 Python이 흔하다.
- 가정: 로컬은 stdio, 팀 공유·GCP 호스팅은 Streamable HTTP.
- 미확인: `purple-context-mcp`의 실제 transport, 배포(Cloud Run 등), OAuth vs 서비스 계정, 노출 Google API 목록.
- 이 저장소에서는 `.cursor/` 승격·실제 MCP 서버 구현을 하지 않는다.

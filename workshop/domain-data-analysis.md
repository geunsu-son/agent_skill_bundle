# 작업 아이디어 정의

## 작업 이름

도메인 기반 데이터 분석 설계와 의사결정자용 해석

## 해결하려는 문제

Agent에게 분석을 맡기면 도메인과 질문과 무관하게 같은 파이프라인(요약 통계 → 상관 → 모델 → 차트)으로 들어가는 경우가 많다. 그러면 다음이 빠진다.

- 이 데이터가 **무엇을 결정하기 위한 분석인지** 먼저 고르기
- 도메인에서 우선 볼 기법(퍼널, 세그먼트, 드라이버, 개인 궤적 등)을 질문·데이터 입도에 맞게 고르기
- 종속변수·설명변수를 충분히 탐색한 뒤 분석 설계하기
- 분석가끼리 공유하기 좋은 노트북이 아니라, 임원·실무 의사결정자가 바로 쓸 해석 쓰기

설계 탐색이 얕으면 이후 검증과 보고서 품질도 같이 떨어진다.

## Agent가 수행할 작업

1. 분석 대상(도메인), 의사결정 질문, 독자를 먼저 확정한다.
2. 질문 유형과 데이터 입도에 맞는 기법 후보를 고르고, 불가능한 기법은 억지로 적용하지 않는다.
3. 종속변수와 설명변수를 설계 메모로 남긴 뒤에야 분석을 실행한다.
4. 설계가 버틸 수 있는지 검증(홀드아웃, 기간 분할, 세그먼트 강건성)한다.
5. 임원·소비자 등 비분석가 독자에게 무엇을 강조할지, 어떤 단위로 표현할지 정해 보고서를 쓴다.

## 기대 결과물

- 분석 설계 메모: 질문, 도메인, 채택 기법, 종속/설명변수, 하지 않을 분석
- 검증 요약: 무엇이 버텼고 무엇이 깨졌는지
- 의사결정자용 보고서: 한눈에 보기, 의미, 한계, 다음에 할 행동
- (분석가용 상세는 부록. 본문이 되지 않음)

## 현재 방식과 불편한 점

일반적인 Agent 분석은 EDA와 모델 지표를 먼저 쌓는다. 도메인 기법은 사후에 붙고, 보고서는 차트 나열에 가깝다. 사용자는 다시 해석해야 한다.

## 실행 시점 또는 조건

분석 요청이 들어왔을 때. 정기 스케줄은 두지 않는다.

## 판단 기준과 제약

- 도메인 레이블만으로 기법을 고정하지 않는다. 질문과 데이터 입도가 기법을 걸러낸다.
- 인과를 관측 연관으로 단정하지 않는다.
- 사실, 추정, 권고를 구분한다.
- 개인정보·식별 가능한 개인 기록을 보고서에 넣지 않는다.
- 첫 검증 도메인은 사용자가 제시한 **매출·마케팅**과 **학습** 두 가지로 제한한다.

## 완료 조건

- 설계 메모 없이 모델·차트부터 나오지 않음
- 채택 기법과 탈락 기법의 이유가 남아 있음
- 보고서 본문이 비분석가 독자 기준으로 읽힘
- 한계와 다음 확인 항목이 있음

## 가정과 아직 결정하지 못한 점

가정:

- 첫 시험은 캐글의 공개 데이터로 한다. 사내 데이터 스키마는 아직 고정하지 않는다.
- 백테스트는 트레이딩 백테스트가 아니라, 설계한 분석이 다른 기간·집단에서도 버틸지 보는 검증을 뜻한다.
- 보고서 1차 독자는 임원·실무 의사결정자이고, 소비자용 표현은 같은 결과의 번역 레이어로 둔다.

아직 결정하지 못한 점:

- 도메인 카드를 몇 개까지 늘릴지. 지금은 마케팅·학습만 시드로 둔다.
- 캐글 실행 코드를 Script로 분리할지. 같은 전처리가 두 번 반복되기 전에는 후보로만 둔다.
- 분석가용 상세 산출물을 항상 남길지, 요청 시에만 남길지.

## 작은 실험

캐글 데이터 두 건으로 Skill을 한 번씩 실행한다.

1. 마케팅: 거래 데이터에서 세그먼트·기여 분석이 퍼널보다 먼저 나오는지
2. 학습: 점수 데이터에서 드라이버 분석이 나오고, 개인 추적이 데이터 입도상 불가능한지 명시되는지

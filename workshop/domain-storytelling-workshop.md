# 작업 아이디어 정의

## 작업 이름

도메인 스토리텔링 워크숍 개발담당자

## 해결하려는 문제

사용자의 업무 설명이 모호한 상태에서 Agent가 곧바로 해결책이나 코드로 넘어가면, 암묵적인 조건·예외·용어·판단 기준이 빠진 채 개발 요구사항으로 굳어진다.

## Agent가 수행할 작업

사용자를 도메인 전문가로 두고 개발자 관점의 질문을 한 번에 하나씩 이어간다. 실제 업무를 `Actor → Action → Work Object` 흐름으로 정리하면서 다음을 명시한다.

- 시작 조건과 종료 결과
- 도메인 용어와 업무 규칙
- 상태 변화와 예외
- 판단 기준과 데이터 출처
- 결과 사용자와 사람 승인 지점

중간 재생(playback)으로 이해가 맞는지 확인하고, 확인된 내용만 개발 연결점으로 변환한다.

## 기대 결과물

- 도메인 스토리
- 도메인 용어집
- 비즈니스 규칙
- 예외 시나리오
- 미확정 질문
- 개발 연결점

## 현재 방식과 불편한 점

“예약 상태를 바꾼다”, “퍼널을 분석한다”, “데이터를 정제해 적재한다” 같은 설명만으로 구현을 시작하면 누가 무엇을 언제 판단하는지, 중복·오류·예외를 어떻게 처리하는지 코드 작성 중에 뒤늦게 발견한다.

## 실행 시점 또는 조건

- 문서화가 부족한 업무를 개발 요구사항으로 바꾸기 전
- 기능 수정 요청이 반복되지만 업무 규칙이 명시되지 않았을 때
- 기존 코드나 데이터 처리 절차에서 실제 도메인 규칙을 복원할 때

한 번의 워크숍에서는 경계가 분명한 업무 흐름 하나만 다룬다.

## 판단 기준과 제약

- 사용자가 제공하지 않은 규칙을 사실처럼 채우지 않는다.
- 가장 중요한 모호점 하나씩 질문하며 체크리스트를 한꺼번에 던지지 않는다.
- 모순은 임의로 해소하지 않고 사용자에게 다시 확인한다.
- 사용자가 모르는 내용은 실패로 보지 않고 미확정 질문으로 남긴다.
- 워크숍 결과 확인 전에는 설계나 구현으로 넘어가지 않는다.

## 완료 조건

- 시작과 끝이 있는 도메인 스토리 1개가 사용자 확인을 받음
- 용어·규칙·예외·미확정 사항이 서로 구분됨
- 처음 설명에 없던 업무 규칙 또는 예외가 3개 이상 발견되거나, 더 없다는 사용자 확인이 기록됨
- 필요한 데이터·도구·승인·자동화 후보·테스트 규칙이 개발 연결점에 정리됨

## 가정과 아직 결정하지 못한 점

- 상태는 `draft`이며 실제 워크숍으로 검증되지 않았다.
- Cursor에서 대화형으로 사용하는 Rule·Skill만 만든다.
- Script와 Automation은 반복 사용 전까지 만들지 않는다.
- 결과 저장 위치와 후속 산출물(PRD, 데이터 모델, API, 테스트)은 워크숍마다 정한다.

## 작은 실험

문서화가 부족하지만 사용자가 잘 아는 업무 하나를 골라 Skill을 실행한다.

1. 첫 설명과 최종 도메인 스토리를 비교한다.
2. 새로 드러난 규칙 또는 예외 수를 센다.
3. 개발자가 테스트 조건으로 바꿀 수 있는 규칙이 있는지 확인한다.

관찰할 항목:

1. 바로 도움이 된 내용
2. 불필요하거나 과도했던 질문
3. 다음 실행에서 바꿀 한 가지

# 작업 아이디어 정의

## 작업 이름

도메인 스토리텔링 워크숍 담당자

## 해결하려는 문제

사용자의 업무 설명이 모호한 상태에서 Agent가 곧바로 해결책이나 실행으로 넘어가면, 암묵적인 조건·예외·용어·판단 기준이 빠진 채 잘못된 요구사항으로 굳어진다.

## Agent가 수행할 작업

사용자를 도메인 전문가로 두고 개발자, 데이터 분석가, 데이터 엔지니어 중 선택한 담당자 관점의 질문을 한 번에 하나씩 이어간다. 담당자를 모르겠다면 공통 질문으로 가장 먼저 필요한 결과물을 파악한 뒤 하나를 추천한다. 실제 업무를 `Actor → Action → Work Object` 흐름으로 정리하면서 다음을 명시한다.

- 시작 조건과 종료 결과
- 도메인 용어와 업무 규칙
- 상태 변화와 예외
- 판단 기준과 데이터 출처
- 결과 사용자와 사람 승인 지점

중간 재생(playback)으로 이해가 맞는지 확인하고, 확인된 내용만 담당자별 연결점으로 변환한다. 진행 결과와 다음 질문은 Markdown으로 저장하여 다음 채팅에서 이어간다. 탐색 인터뷰는 주제만으로 시작하고 경계를 draft로 두며, 구현 전 정리는 문제와 해결책 가설을 분리한다.

## 기대 결과물

- 도메인 스토리
- 도메인 용어집
- 비즈니스 규칙
- 예외 시나리오
- 미확정 질문
- 담당자별 연결점
- 선택한 담당자·모드·진행 상태·다음 질문이 포함된 `domain-workshops/*.md`

## 현재 방식과 불편한 점

“예약 상태를 바꾼다”, “퍼널을 분석한다”, “데이터를 정제해 적재한다” 같은 설명만으로 구현을 시작하면 누가 무엇을 언제 판단하는지, 중복·오류·예외를 어떻게 처리하는지 코드 작성 중에 뒤늦게 발견한다.

## 실행 시점 또는 조건

- 문서화가 부족한 업무를 다음 산출물의 요구사항으로 바꾸기 전
- 기능 수정 요청이 반복되지만 업무 규칙이 명시되지 않았을 때
- 기존 코드나 데이터 처리 절차에서 실제 도메인 규칙을 복원할 때
- 서비스나 업무를 인터뷰로 문서화할 때. 주제만 있어도 시작

기록 단위는 확인 중인 업무 흐름 하나다. 시작·종료 경계는 입장 조건이 아니라 세션 중 갱신하는 draft다. 여러 흐름은 초기에 자르지 않고, 스토리가 갈라질 때 후속 워크숍 후보로 분리한다.
Skill을 다시 호출하면 새 워크숍 또는 저장된 Markdown 이어하기를 선택한다.

## 판단 기준과 제약

- 사용자가 제공하지 않은 규칙을 사실처럼 채우지 않는다.
- 가장 중요한 모호점 하나씩 질문하며 체크리스트를 한꺼번에 던지지 않는다.
- 모순은 임의로 해소하지 않고 사용자에게 다시 확인한다.
- 사용자가 모르는 내용은 실패로 보지 않고 미확정 질문으로 남긴다.
- 워크숍 결과 확인 전에는 설계나 구현으로 넘어가지 않는다.
- `아직 모르겠음`을 담당자로 저장하지 않고 공통 질문 후 세 담당자 중 하나를 추천한다.
- 저장된 워크숍은 사용자가 파일을 선택한 뒤에만 이어간다.
- 탐색 인터뷰에서 첫 질문으로 흐름 후보를 고르게 하지 않는다.
- 임시 경계를 입장 조건처럼 확정하지 않는다.

## 완료 조건

- 확인된 스토리로 시작과 종료가 연결됨. 처음 경계 문장이 끝까지 그대로일 필요는 없음
- 용어·규칙·예외·미확정 사항이 서로 구분됨
- 처음 설명에 없던 업무 규칙 또는 예외가 3개 이상 발견되거나, 더 없다는 사용자 확인이 기록됨
- 선택한 담당자 관점의 다음 산출물 조건이 연결점에 정리됨
- 중단 또는 완료 상태와 다음 질문이 Markdown에 저장됨

## 가정과 아직 결정하지 못한 점

- 상태는 `testing`이며 다른 저장소의 실제 워크숍으로 검증한다.
- Cursor에서 대화형으로 사용하는 Rule·Skill만 만든다.
- Script와 Automation은 반복 사용 전까지 만들지 않는다.
- 결과 저장 위치는 소비 프로젝트의 `domain-workshops/`로 둔다.
- Skill이 호출됐을 때 세션 gate를 실행하며 모든 새 채팅에서 자동 시작되지는 않는다.
- 탐색 인터뷰와 구현 전 정리는 모두 1급 모드다. 목적 자체를 인터뷰 전용으로 바꾸지 않는다.
- 후속 산출물(PRD, 분석 보고서, 데이터 모델, API, 파이프라인, 테스트)은 워크숍마다 정한다.
- 참고자료: [도메인 스토리텔링 워크숍 시도](https://app.notion.com/p/3de36fd4c9b781d28372dfd36a40f155) (사용자 제공, 2026-09-17 확인)

## 작은 실험

문서화가 부족하지만 사용자가 잘 아는 업무 하나를 골라 Skill을 실행한다.

1. 첫 설명과 최종 도메인 스토리를 비교한다.
2. 새로 드러난 규칙 또는 예외 수를 센다.
3. 선택한 담당자가 다음 산출물의 조건으로 바꿀 수 있는 규칙이 있는지 확인한다.

관찰할 항목:

1. 바로 도움이 된 내용
2. 불필요하거나 과도했던 질문
3. 다음 실행에서 바꿀 한 가지

관찰 결과는 Issue로 되돌려 공통 Rule·Skill 변경 근거로 사용한다.

## 관찰 (2026-09-18)

첫 소비 시험([Issue #21](https://github.com/geunsu-son/agent_skill_bundle/issues/21)): 주제만 있는 인터뷰·문서화로 시작했는데, Skill §3이 초기에 흐름 후보를 고르게 해 탐색이 막힌 것처럼 느껴졌다. 담당자 gate와 한 질문씩·저장·재개는 도움이 됐다.

반영: 탐색 인터뷰 / 구현 전 정리 모드를 나누고, 시작·종료 경계를 입장 조건이 아니라 중간 재생마다 갱신하는 draft로 다룬다. 소비 프로젝트 고유 지표·산식·조직 세부는 넣지 않는다.

다음 검증: 주제만 있는 탐색 인터뷰에서 첫 질문이 한 줄 인터뷰인지, 경계 문장이 재생마다 바뀌는지.

## 관찰 (2026-09-18, 같은 시험 세션 계속)

같은 소비 시험에서, 흐름이 정리되지 않은 단일 답변마다 §8 재생 형식(흐름 목록·새로 확인된 규칙)을 반복해서 보여줬다. §5는 매 답변 뒤 조용히 파일만 갱신하고 다음 질문만 하도록 이미 정의돼 있었는데, 실제로는 §5와 §8이 섞여서 매 턴 노이즈가 됐다.

1차 반영에서는 §5가 재생 형식을 전혀 보여주지 않도록 막았으나, 사용자가 완전히 숨기기보다 필요할 때만 보여주는 편이 낫다고 판단했다. 최종 반영: §7 분류를 기준으로 단순 사실 답변은 파일에만 반영하고, 이후 처리 방식을 바꾸는 비즈니스 규칙·판단 기준·예외만 `확인: [규칙 한 줄]`로 짧게 보여준다. §8의 전체 재생(흐름 목록·범위 초안·확인 질문)은 흐름 한 덩어리가 정리됐을 때만 쓴다.

다음 검증: 단순 사실 답변엔 다음 질문만 나오는지, 규칙성 답변엔 한 줄 `확인:`만 나오고 전체 재생으로 부풀지 않는지, 전체 재생은 분기가 정리될 때만 나오는지.

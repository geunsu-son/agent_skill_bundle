# 작업 아이디어 정의

## 작업 이름

도메인 스토리텔링 워크숍 담당자

## 해결하려는 문제

사용자의 업무 설명이 모호한 상태에서 Agent가 곧바로 해결책이나 실행으로 넘어가면, 암묵적인 조건·예외·용어·판단 기준이 빠진 채 잘못된 요구사항으로 굳어진다.

## Agent가 수행할 작업

사용자를 도메인 전문가로 두고 Agent는 **워크숍 담당자**로서 도메인 질문을 한 번에 하나씩 이어간다. 실제 업무를 `Actor → Action → Work Object` 흐름으로 정리하면서 다음을 명시한다.

- 시작 조건과 종료 결과
- 도메인 용어와 업무 규칙
- 상태 변화와 예외
- 판단 기준과 데이터 출처
- 결과 사용자와 사람 승인 지점

중간 재생(playback)으로 이해가 맞는지 확인하고, 확인된 뒤에만 (선택) 연결점으로 옮긴다. 진행 결과와 다음 질문은 Markdown으로 저장하여 다음 채팅에서 이어간다. 탐색 인터뷰는 주제만으로 시작하고 경계를 draft로 두며, 구현 전 정리는 문제와 해결책 가설을 분리한다.

## 기대 결과물

- 도메인 스토리
- 도메인 용어집
- 비즈니스 규칙
- 예외 시나리오
- 미확정 질문
- (선택) 연결점
- `role: workshop-facilitator`·모드·진행 상태·다음 질문이 포함된 `domain-workshops/*.md`

## 현재 방식과 불편한 점

“예약 상태를 바꾼다”, “퍼널을 분석한다”, “데이터를 정제해 적재한다” 같은 설명만으로 구현을 시작하면 누가 무엇을 언제 판단하는지, 중복·오류·예외를 어떻게 처리하는지 코드 작성 중에 뒤늦게 발견한다.

## 실행 시점 또는 조건

- 문서화가 부족한 업무를 다음 산출물의 요구사항으로 바꾸기 전
- 기능 수정 요청이 반복되지만 업무 규칙이 명시되지 않았을 때
- 기존 코드나 데이터 처리 절차에서 실제 도메인 규칙을 복원할 때
- 서비스나 업무를 인터뷰로 문서화할 때. 주제만 있어도 시작

기록 단위는 확인 중인 업무 흐름 하나다. 시작·종료 경계는 입장 조건이 아니라 세션 중 갱신하는 draft다. 여러 흐름은 초기에 자르지 않고, 스토리가 갈라질 때 후속 워크숍 후보로 분리한다.
Skill을 다시 호출하면 새 워크숍 또는 저장된 Markdown 이어하기를 선택한다.

## 판단 기준과 제약

- 사용자가 제공하지 않은 규칙을 사실처럼 채우지 않는다.
- 복원할 as-is가 없는 주제는 입장에서 걸러내거나 `범위 예외`로 기록한다.
- 가장 중요한 모호점 하나씩 질문하며 체크리스트를 한꺼번에 던지지 않는다. 모든 도메인 질문에 Agent의 추측을 붙인다.
- 사용자가 새로 결정해야 답할 수 있는 질문은 내지 않는다. 진행 속도와 남은 범위는 담당자가 관리한다.
- 모순은 임의로 해소하지 않고 사용자에게 다시 확인한다.
- 사용자가 모르는 내용은 실패로 보지 않고 미확정 질문으로 남긴다.
- 워크숍 결과 확인 전에는 설계나 구현으로 넘어가지 않는다. 시스템 설계를 원하면 워크숍을 중단한다.
- 표면 요청은 니즈·해결책 가설로 두고 구현 결정으로 굽지 않는다.
- 인터뷰 중 역할은 `workshop-facilitator`다. 연결점은 확인 후에만, 원할 때 고른다.
- 저장된 워크숍은 사용자가 파일을 선택한 뒤에만 이어간다.
- 탐색 인터뷰에서 첫 질문으로 흐름 후보를 고르게 하지 않는다.
- 임시 경계를 입장 조건처럼 확정하지 않는다.

## 완료 조건

- 확인된 스토리로 시작과 종료가 연결됨. 처음 경계 문장이 끝까지 그대로일 필요는 없음
- 용어·규칙·예외·미확정 사항이 서로 구분되고, 미확정 줄에 확인 주체와 확인 방법이 있음
- 다음 질문 세 개의 답을 예측할 수 있어 질문을 멈췄거나, 예측 불가를 미확정으로 남기고 종료함
- 연결점은 확인 후에만, 사용자가 원할 때만 작성됨
- 중단 또는 완료 상태와 다음 질문이 Markdown에 저장됨

처음 설명에 없던 업무 규칙·예외 수는 완료 조건이 아니라 관찰 지표다. `확인 기록`에 적기만 한다.

## 가정과 아직 결정하지 못한 점

- 상태는 `testing`이며 다른 저장소의 실제 워크숍으로 검증한다.
- Cursor에서 대화형으로 사용하는 Rule·Skill만 만든다.
- Script와 Automation은 반복 사용 전까지 만들지 않는다.
- 결과 저장 위치는 소비 프로젝트의 `domain-workshops/`로 둔다.
- Skill이 호출됐을 때 세션 gate를 실행하며 모든 새 채팅에서 자동 시작되지는 않는다.
- 탐색 인터뷰와 구현 전 정리는 모두 1급 모드다. 목적 자체를 인터뷰 전용으로 바꾸지 않는다.
- 인터뷰 중 역할은 `workshop-facilitator`다. 개발자·분석가·데이터 엔지니어는 확인 후 선택적 연결점뿐이다.
- 후속 산출물(PRD, 분석 보고서, 데이터 모델, API, 파이프라인, 테스트)은 워크숍마다 정한다.
- 참고자료: [도메인 스토리텔링 워크숍 시도](https://app.notion.com/p/3de36fd4c9b781d28372dfd36a40f155) (사용자 제공, 2026-09-17 확인)

## 작은 실험

문서화가 부족하지만 사용자가 잘 아는 업무 하나를 골라 Skill을 실행한다.

1. 첫 설명과 최종 도메인 스토리를 비교한다.
2. 새로 드러난 규칙 또는 예외 수를 센다.
3. 연결점은 확인 후에만, 사용자가 원할 때만 나왔는지 확인한다.

관찰할 항목:

1. 바로 도움이 된 내용
2. 불필요하거나 과도했던 질문
3. 다음 실행에서 바꿀 한 가지

관찰 결과는 Issue로 되돌려 공통 Rule·Skill 변경 근거로 사용한다.

## 관찰 (2026-09-18)

첫 소비 시험([Issue #21](https://github.com/geunsu-son/agent_skill_bundle/issues/21)): 주제만 있는 인터뷰·문서화로 시작했는데, Skill의 경계 잡기 절이 초기에 흐름 후보를 고르게 해 탐색이 막힌 것처럼 느껴졌다. 담당자 gate와 한 질문씩·저장·재개는 도움이 됐다.

반영: 탐색 인터뷰 / 구현 전 정리 모드를 나누고, 시작·종료 경계를 입장 조건이 아니라 중간 재생마다 갱신하는 draft로 다룬다. 소비 프로젝트 고유 지표·산식·조직 세부는 넣지 않는다.

다음 검증: 주제만 있는 탐색 인터뷰에서 첫 질문이 한 줄 인터뷰인지, 경계 문장이 재생마다 바뀌는지.

## 관찰 (2026-09-18, 같은 시험 세션 계속)

같은 소비 시험에서, 흐름이 정리되지 않은 단일 답변마다 전체 재생 형식(흐름 목록·새로 확인된 규칙)을 반복해서 보여줬다. 질문 절은 매 답변 뒤 조용히 파일만 갱신하고 다음 질문만 하도록 이미 정의돼 있었는데, 실제로는 질문 절과 재생 절이 섞여서 매 턴 노이즈가 됐다.

1차 반영에서는 질문 절이 재생 형식을 전혀 보여주지 않도록 막았으나, 사용자가 완전히 숨기기보다 필요할 때만 보여주는 편이 낫다고 판단했다. 최종 반영: 상태·규칙·예외 분류를 기준으로 단순 사실 답변은 파일에만 반영하고, 이후 처리 방식을 바꾸는 비즈니스 규칙·판단 기준·예외만 `확인: [규칙 한 줄]`로 짧게 보여준다. 전체 재생(흐름 목록·범위 초안·확인 질문)은 흐름 한 덩어리가 정리됐을 때만 쓴다.

다음 검증: 단순 사실 답변엔 다음 질문만 나오는지, 규칙성 답변엔 한 줄 `확인:`만 나오고 전체 재생으로 부풀지 않는지, 전체 재생은 분기가 정리될 때만 나오는지.

## 관찰 (2026-09-19, Issue #24)

소비 시험([Issue #24](https://github.com/geunsu-son/agent_skill_bundle/issues/24), `trading-to-fire`): 형식·게이트·저장·`confirmed`까지는 키트를 따랐으나, to-be 봇 주제에서 질문이 **구현 유도**처럼 느껴졌고 기존 AI 개발 Q&A와 형식만 다르다는 마찰이 있었다. 진단은 **주제 한계(as-is가 얇음)** + **역할 드리프트(담당자 결정을 사용자에게 물음)** 혼합.

채택 (공용 절차):

- 목적을 **현재 업무·암묵지 문서화**로 명시. 개발/시스템 설계 워크숍이 아님을 Rule·Skill에 적음
- 표면 “만들면 좋겠어요” → 니즈로 기록하고 실무를 더 깊게 묻기. 니즈 확인 후 설계를 굽지 않기
- 시스템/개발 설계 모드가 계속되면 목적 안내 후, 설계를 원하면 워크숍 **중단**
- 중도 “처음부터” 시 덮어쓰기 vs 새 파일명 확인

추가 채택 (같은 피드백 후속, 역할 구조 B):

- 인터뷰 역할은 **워크숍 담당자**만. 개발자·분석가·데이터 엔지니어 gate는 입장에서 제거
- 연결점은 확인 후·선택. `connection_role`로 분리. 생략 가능
- 예전 파일의 `role: developer|...`는 이어하기 시 facilitator로 읽고 연결 후보로만 참고

보류:

- 탐색 인터뷰 / 구현 전 정리 1급 모드 구조는 유지 (#21). 목적만 인터뷰 전용으로 바꾸지 않음
- 소비 특수(트레이딩 SSOT·OKX·텔레그램 등)는 Skill에 넣지 않음
- 세탁기 비유 전문은 Skill에 장문으로 넣지 않고, 목적 한 줄 비유로만 남김

다음 검증: 역할 gate 없는 인터뷰가 구현 유도 체감을 줄이는지, 연결점 생략이 자연스러운지, to-be 주제에서도 니즈 심화·설계 중단 gate가 걸리는지.

## 관찰 예정 (2026-09-21)

반영: 고정 선택지 gate(세션·모드·설계 중단·연결점·파일 덮어쓰기)는 Skill에 `AskQuestion` 사용을 명시. 도메인·재생 질문은 채팅 유지. `text` 블록은 문구 SSOT, 도구 불가 시 폴백.

다음 검증: gate가 클릭 UI로 한 턴에 하나 나오는지, 도메인 질문이 선택지로 잘못 바뀌지 않는지.

## 지침 점검 (2026-09-21, 외부 사례 대조)

소비 시험이 아니라 **문서 자체 점검**이다. 기준은 스킬의 목적 정합성, 실행 가능성, 금지 대비 지시 균형, #21·#24 원인 대응, 중복, 완료 판정 가능성, 설치·발견 정합성 7축.

진단:

- 금지 문장은 Skill·Rule·README 합쳐 약 40줄인데 질문 견본은 1개였다. 인터뷰 스킬의 1차 산출물이 질문인데 좋은 질문의 예가 거의 없었다.
- #24가 진단한 두 원인 중 **주제 한계(as-is 얇음)** 에 대응하는 절차가 없었다. 역할 드리프트만 반영돼 있었다.
- #24 마찰 3번(진행·효율을 사용자가 제시함)에 대응하는 진행 주도 지침이 없었다.
- 설계 중단 gate 트리거가 “여러 턴에 걸쳐”뿐이라 판정이 불가능했다.
- SKILL.md에 frontmatter가 없어 “해결책만 요청받아도 먼저 사용”이라는 선제 호출 기대가 실제로 동작하지 않았다.

대조한 외부 사례:

- [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) — `docs/skill-anatomy.md`의 frontmatter 계약(what + when), Common Rationalizations 표, 증거 기반 Verification, 500줄 상한, 스킬 간 내용 중복 금지. 같은 장르인 `skills/interview-me`의 가설·확신도, Q+GUESS 형식, 예측 가능성 정지 테스트, 종료 턴 STOP 규칙.
- [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) — 처음 걸리는 단에서 멈추는 사다리 구조, grep 가능한 `ponytail:` 마커에 한계와 후속 경로를 함께 적는 방식.
- [alibaba/open-code-review](https://github.com/alibaba/open-code-review) — 규칙마다 실행 가능한 검사, 좁은 예외를 우선하는 escape hatch(`allow-non-english: <reason>`).

반영:

- Skill에 `name`/`description` frontmatter 추가. 발동 조건과 비적용 주제를 description에 넣음
- `사용하지 않을 때` + 입장 확인 1문항(지금 하고 있음 / 과거 수동 / 아직 없음)과 `범위 예외` 마커 추가
- 모든 도메인 질문에 추측 붙이기, 처음 걸리는 단에서 멈추는 질문 사다리, “어제 한 일에서 답이 나오는가” 판별 테스트와 대조 예시
- 설계 감지는 2턴 연속, 종료는 다음 질문 세 개 예측 가능성 테스트로 교체. 최종 확인 턴에서 멈추는 규칙 추가
- 중간 재생에 이해도 한 줄, `[초안]` 줄에 확인 주체·확인 방법 필수화
- 실패 목록을 「흔한 자기합리화」 표와 「실패 신호」로 재구성. Rule과 README의 사본은 참조로 대체

다음 검증(다음 소비 시험에서 확인할 것):

1. as-is가 얇은 주제가 입장 확인에서 실제로 걸리는가, 아니면 사용자가 1번을 골라 통과시키는가
2. 추측이 붙은 질문에 사용자가 더 빨리·구체적으로 답하는가. 추측이 틀렸을 때 교정이 나오는가, 아니면 동의만 하는가
3. “어제 한 일에서 답이 나오는가” 테스트가 구현 유도 질문을 실제로 걸러내는가
4. 종료가 질문 소진이 아니라 예측 가능성 테스트로 일어나는가
5. 이해도 한 줄이 진행 주도 체감을 바꾸는가, 아니면 노이즈로 느껴지는가

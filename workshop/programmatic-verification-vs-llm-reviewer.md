# 작업 아이디어 정의

## 작업 이름

프로그램 검증을 LLM reviewer보다 먼저 두는 게이트

## 상태

`idea` — 영상 1건과 현재 번들 문서를 대조한 관찰. 실제 사용으로 검증하지 않음. Rule·Skill·Script로 승격하지 않음.

## 해결하려는 문제

Agent Thinking Guidelines의 검증 경로가, 코드로 끝나는 검사까지 `/reviewer` 서브에이전트에 넘기는 쪽으로 기울어 있다.

## Agent가 수행할 작업

아직 없음. 이번 기록은 검토 결과다.

## 기대 결과물

아직 없음. 다음 실험이 정해지면 최소 예시로 옮긴다.

- **가정**: 제작자·전체 맥락은 자막 밖이라 단정하지 않는다.

## 영상 주장 (자막 기준)

에이전트를 잘못 쓰는 특징은 검증을 무조건 서브에이전트(또는 Codex)에 맡기는 것이다. 대부분의 검증은 프로그램으로 할 수 있고, 그게 더 빠르다. 프로그램으로 되는 일을 LLM에 시키는 것은 잘못된 하네스다.

## 현재 방식과 불편한 점

현재 검증 스택은 거의 전부 LLM 판정이다.

```text
Worker 자체 검토(5장 체크리스트, LLM)
  → reviewer 서브에이전트(같은 체크리스트, LLM)
  → 통과/반려 루프 (최대 3회)
```

분석 프로토콜은 행 수 기록·집계 역산을 요구하지만, 실행 주체는 스크립트가 아니라 모델이다. 수치가 있으면 그 다음에도 reviewer를 타게 되어 있다.

`analysis-protocol`의 마지막 단계:

> 최종 보고 전, 수치가 포함되어 있으면 reviewer 서브에이전트 검증을 거친다.

번들 안에 `scripts/`는 없다. 결정론적 로직을 Script로 빼라는 공방 기준(`docs/rule-vs-skill.md`, `idea-to-agent-artifact`)과 어긋난다.

이미 같은 방향인 부분:

- `worker-conduct` 1.5: 도구 결과 없이 “완료/테스트 통과”를 말하지 않는다.
- Core User Rule §4: 검증 우선순위는 테스트 → 린터/타입체커/기존 스크립트 → 최소 재현.
- reviewer는 열린 평가가 아니라 항목별 판정이다.
- heavy workflow는 opt-in이라 일상 수정까지 reviewer를 켜지 않는다.

## 판단 기준과 제약

프로그램으로 닫히는 항목과 판단이 남는 항목을 섞지 않는다.

| 항목 | 현재 | 제안 |
|---|---|---|
| 표 합계·비율·파이프라인 행 수 | reviewer가 더함 | 노트북/SQL/스크립트 |
| 테스트·린트·타입체크 통과 | 모델이 주장할 수 있음 | 명령 실행 결과 |
| 필수 섹션·제출 필드 존재 | 형식 준수(LLM) | 스키마·존재 검사 |
| 가정 태그 존재 | LLM | 단순 패턴 검사(후보) |
| 요청 충족·논리 비약 | LLM | LLM 유지 |
| 가정 타당성·반례 | LLM | LLM 유지 |
| 상관/인과 해석 | LLM | LLM 유지 |

## 완료 조건

이번 기록의 완료 조건은 아래뿐이다.

- 영상 주장을 자막 기준으로 적었다.
- 현재 ATG 검증 경로와 대조했다.
- 적용 가능한 부분과 아닌 부분을 나눴다.
- 번들 SSOT는 바꾸지 않았다.

## 가정과 아직 결정하지 못한 점

- 영상 화면의 “잘 된 하네스”가 구체적으로 어떤 검사인지는 미확인.
- 수치 보고마다 reviewer를 건너뛰는 것이 실제로 비용을 줄이는지는 미검증.
- 설계 문서처럼 판단이 본인 작업에서는 프로그램 게이트의 이득이 작을 수 있다.

### 가설

공통 Rule로 올리지 않는다. 쓸 곳이 생기면 Skill 한 줄(검사 종류를 가른 뒤 reviewer로 보낸다)과, 반복되는 결정론적 검사만 Script로 뺀다.

### 작은 실험

한 번의 수치 분석에서만 시험한다.

1. Worker가 합계·행 수를 프로그램으로 맞춘다.
2. reviewer에는 해석·가정·요청 충족만 넘긴다.
3. 시간·재작업·놓친 오류를 기존 “전부 reviewer”와 비교한다.

범용 검증 엔진은 만들지 않는다.

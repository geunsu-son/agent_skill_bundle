## 영상 주장 (자막 기준)

에이전트를 잘못 쓰는 특징은 검증을 무조건 서브에이전트(또는 Codex)에 맡기는 것이다. 대부분의 검증은 프로그램으로 할 수 있고, 그게 더 빠르다. 프로그램으로 되는 일을 LLM에 시키는 것은 잘못된 하네스다.

## 현재 방식과 불편한 점

현재 검증 스택은 거의 전부 LLM 판정이다.

```text
Worker 자체 검토(5장 체크리스트, LLM)
  → reviewer 서브에이전트(같은 체크리스트, LLM)
  → 통과/반려 루프 (최대 3회)
```

분석 프로토콜은 행 수 기록·집계 역산을 요구하지만, 실행 주체는 스크립트가 아니라 모델이다. 수치가 있으면 그 다음에도 reviewer를 타게 되어 있다.

이미 같은 방향인 부분: `worker-conduct` 1.5, Core User Rule §4, reviewer 항목별 판정, heavy workflow opt-in.

## 실험 (2026-09-12)

### 설계

분석 질문: 계약 유형별로 이탈률이 얼마나 다르고, 그 순위가 인터넷 서비스 유형 안에서도 유지되는가?

데이터:

- 캐글 공개 [Telco Customer Churn](https://www.kaggle.com/datasets/blastchar/telco-customer-churn) (무료)
- Kaggle CLI 없음. IBM 공개 미러로 동일 CSV를 받음
- 7,043행, 고객키 중복 0. 단위=고객

원본 집계(**확인됨**, pandas):

- 전체 이탈 1,869/7,043 = 26.5%
- Month-to-month 1,655/3,875 = 42.7%
- One year 166/1,473 = 11.3%
- Two year 48/1,695 = 2.8%
- Fiber optic × Month-to-month 1,162/2,128 = 54.6%
- 인터넷 3유형 모두 월간 계약 이탈률이 가장 높음

Worker 초안에는 아래를 **심어** 두었다. 자연 발생 오류가 아니라 검출용 설계다.

| ID | 종류 | 초안 주장 | 원본 |
|---|---|---|---|
| E1 | 수치 | 한눈에 보기 월간 이탈률 55.0% | 42.7% |
| E2 | 수치 | Two year n=1,795, 세그먼트 합 7,143 | n=1,695, 합 7,043 |
| E3 | 수치 | Fiber×월간 이탈 1,297 | 1,162 |
| E4 | 판단 | “월간 계약이 이탈을 유발한다” | 연관만 확인됨 |

Path A: `reviewer.md` 전체 체크리스트. 초안+CSV만 제공. 정답·심은 오류 목록은 숨김. 표는 직접 더하고 원본 역산은 최소 1개.

Path B: 같은 초안을 스크립트가 먼저 검사(행 수, 세그먼트 합, 비율, 지정 1셀 역산, 필수 절 존재). 그다음 다른 서브에이전트가 수치를 재계산하지 않고 판단 항목만 판정.

분석·검증 스크립트, CSV, 초안, 판정서는 `/tmp`에서 실행했고 실험 후 삭제했다. 저장소에는 이 관찰만 남긴다.

### 관찰

**수치 슬라이스 — 효율 개선이 확인됨.**

- Path B 스크립트: 23ms, 심은 수치 오류 E1·E2·E3를 모두 실패로 표시(실패 5줄: Two year n/rate, 세그먼트 합, 헤드라인 55%, Fiber 이탈 수).
- 프로토콜이 요구하는 “최소 1개 역산”보다 커버리지가 크다. 모든 주장 숫자를 원본과 대조한다.
- Path A도 이번엔 E1·E2·E3를 잡았다. 표 합산으로 E1·E2, Fiber 셀 역산으로 E3. 다만 역산 대상을 다른 셀(예: 전체 1,869/7,043)로 고르면 E3는 프로토콜상 안 봐도 된다.
- Path A 수치 작업은 전용 스크립트가 아니라 리뷰 대화 안에서의 임시 계산이다. 결과는 같아도 반복·완결 보장은 스크립트 쪽이 크다.

**전체 게이트 벽시계 — 큰 차이는 안 났다.**

- Path A 서브에이전트 벽시계: 시작 11:02:42Z → 판정서 11:05:09Z, 약 147초. 자기보고 620초는 벽시계와 불일치라 쓰지 않음.
- Path B: 스크립트 23ms + 판단 서브에이전트 약 125초(11:02:42Z → 11:04:47Z).
- 판단용 LLM이 시간을 지배한다. 수치만 프로그램으로 빼도, reviewer를 그대로 켜면 끝-끝 시간은 비슷하다.
- 영상 주장은 “수치 검사를 LLM/서브에이전트에 넘기지 말라”에 해당한다. “reviewer 전체를 없애면 항상 빨라진다”는 이 1건으로 확인되지 않음.

**판단 슬라이스 — 프로그램으로 대체 불가.**

- E4(인과 단정)는 스크립트가 검사하지 않는다고 명시했다. Path A·Path B 판단 리뷰어 모두 논리/불확실성/가정에서 실패로 잡았다.
- 요청 충족은 갈렸다. Path A는 인터넷 유형별 교차표 부재를 실패, Path B는 문장으로 답했다고 통과. 같은 초안에 대한 LLM 분산이다.

### 가설 (실험 후)

공통 Rule로 올리지 않는다. 쓸 곳이 생기면 analysis-protocol에 한 줄만 후보로 둔다: 합계·행 수·비율·역산은 프로그램으로 먼저 닫고, reviewer는 남는 판단만 본다. 반복되는 검사만 Script로 뺀다.

범용 검증 엔진은 만들지 않는다.

## 완료 조건

- 영상 주장과 현재 ATG 경로를 대조했다.
- 캐글 공개 데이터 1건으로 Path A/B를 돌렸다.
- 효율이 난 구간(수치)과 안 난 구간(끝-끝 시간, 판단)을 나눴다.
- 테스트 코드는 삭제했고, 관찰만 남겼다.
- 번들 SSOT는 바꾸지 않았다.

## 가정과 아직 결정하지 못한 점

- 오류를 심었으므로 현장 에이전트 실수 분포와 같다고 말할 수 없다.
- 서브에이전트 2개는 같은 모델 계열이다. 다른 모델 reviewer는 수치를 더 놓칠 수 있다(**추정**).
- 설계 문서처럼 숫자가 거의 없는 작업에서는 프로그램 게이트 이득이 작을 수 있다.
- analysis-protocol / reviewer 문구 수정은 이 1건만으로 하지 않는다.
